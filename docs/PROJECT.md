## 1. 프로젝트의 목적

포켓몬 챔피언스를 잘 아는 사용자가 실전용 포켓몬의 능력치를 세부 조정하면서, 자신이 지정한 여러 상대에 대한 스피드·공격·방어 결과를 한눈에 확인하는 계산기다.

사용자는 대비할 상대와 조건을 직접 선택하고, 상대마다 공격·방어·스피드 중 필요한 비교 목적을 하나 이상 지정한다. 내 포켓몬의 능력치를 조정하면 선택한 모든 비교 결과가 한 화면에서 즉시 갱신된다. 한정된 능력치를 배분하면서 공격 성능, 생존 가능성과 스피드를 함께 판단하고, 게임을 실행할 수 없는 상황에서도 세팅을 구상할 수 있도록 한다.

프론트엔드 취업용 프로젝트로서는 입력과 상태 관리, 계산과 화면 갱신, 서버 데이터 저장, 인증, 반응형 사용성, 테스트와 성능 개선을 실제 필요에 따라 다룬다. AI가 많은 구현을 수행하더라도 사용자가 선택 이유와 핵심 동작을 이해하고 설명하는 것이 목표다.

## 2. 대상 사용자와 사용 환경

- 대상은 포켓몬 배틀과 세팅에 익숙한 사용자다.
- 주된 사용 시점은 파티 구성과 실전용 세팅 준비 단계다.
- PC를 핵심 사용 환경으로 삼고, 모바일에서도 입력과 결과 확인이 편리하도록 만든다.
- 시각적 장식보다 입력량, 수정 동선, 정보의 가독성을 우선한다.
- 지원 게임은 포켓몬 챔피언스로 한정한다. 다른 게임·세대를 선택하는 UI는 현재 범위에 없다.

## 3. 핵심 기능

### 3.1 통합 상대 목록과 비교 목적

| 비교 목적 | 계산 방향                                | 핵심 출력                                                |
| --------- | ---------------------------------------- | -------------------------------------------------------- |
| 스피드    | 내 포켓몬과 각 상대의 최종 스피드 비교   | 스피드 실수치, 빠름·동속·느림                            |
| 공격      | 내 포켓몬이 선택한 기술로 각 상대를 공격 | 데미지 범위, 쓰러뜨리기까지의 타수와 확률                |
| 방어      | 각 상대의 선택한 기술로 내 포켓몬을 공격 | 받는 데미지 범위, 내 포켓몬이 쓰러지기까지의 타수와 확률 |

- 하나의 내 포켓몬 세팅과 통합 상대 목록을 사용한다.
- 상대마다 공격·방어·스피드 중 비교 목적을 하나 이상 선택한다. 한 상대에 여러 목적을 함께 지정하고 수정할 수 있다.
- 한 상대에 여러 목적을 선택하면 해당 상대의 포켓몬 세팅을 공유한다. 목적별로 같은 상대 세팅을 반복 입력하지 않는다.
- 상대 추가 버튼으로 포켓몬을 고른 뒤 비교 목적, 능력치와 관련 조건을 입력한다. 추가한 상대는 수정하거나 제거할 수 있다.
- 상대가 없는 상태에서 시작할 수 있으며, 처음부터 여러 개의 빈 입력 폼을 채우도록 요구하지 않는다. 통합 목록의 최대 상대 수는 미정이다.
- 내 포켓몬의 능력치 등 입력을 바꾸면 선택한 모든 비교 목적의 결과를 갱신하고 한 화면에서 함께 표시한다.
- 변경 전후 결과를 따로 비교하거나 이전 결과를 자동 이력으로 보관하는 기능은 현재 요구사항에 포함하지 않는다.

### 3.2 입력 조건

챔피언스 싱글 웹 계산기의 입력폼 설계다. 내 포켓몬의 세팅은 모든 상대에게 공유하고, 한 상대의 세팅과 배틀 조건은 그 상대의 공격·방어·스피드 비교에 공유한다.

#### 상시 노출

내 포켓몬 편집 영역과 각 상대의 상세 영역에서 기술·특성 선택과 관계없이 제공하는 항목이다. 상대 행은 필요할 때 펼치고, 중력·트릭룸은 그 행의 접힌 ‘추가 필드’에서 설정한다.

| 입력 항목             | 적용 위치          | 조작과 값                                                                                                                                                                                    |
| --------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 포켓몬·계산할 폼      | 내 포켓몬, 각 상대 | 검색 후 한 항목 선택. 킬가르도는 실드폼·블레이드폼, 돌핀맨은 나이브폼·마이티폼 중 계산할 폼을 고른다. 해당 계산 동안 선택한 폼을 유지한다.                                                   |
| 성격                  | 각 포켓몬          | 성격 한 가지 선택                                                                                                                                                                            |
| 특성                  | 각 포켓몬          | 해당 폼이 가질 수 있는 특성 중 지원하는 데미지·스피드 계산에 쓰이는 것 하나를 선택한다. 미선택 시 특성 효과 없이 계산한다.                                                                   |
| 도구                  | 각 포켓몬          | 하나 선택하거나 비워 둔다. 반감열매는 하나의 선택지로 제공한다.                                                                                                                              |
| 내 기술               | 내 포켓몬          | 해당 폼이 배울 수 있는 계산 대상 기술 중 하나를 선택한다. 공격 비교에 사용하며, 스피드만 비교할 때는 비워 둘 수 있다. 상대 기술의 노출 조건은 아래 표를 따른다.                              |
| 능력치 포인트         | 각 포켓몬          | HP·공격·방어·특공·특방·스피드 6칸. 각각 정수 0~32, 미배분 0, 한 마리 합계 최대 66                                                                                                            |
| 시작 랭크             | 각 포켓몬          | 공격·방어·특공·특방·스피드 5칸. 각각 정수 -6~+6, 기본 0. 시작 시점의 최종 랭크를 입력한다.                                                                                                   |
| 현재 HP               | 각 포켓몬          | **슬라이더와 퍼센트 직접 입력을 함께 제공한다.** 표시된 숫자를 눌러 73을 입력하면 슬라이더도 73%로 이동하고, 슬라이더를 움직이면 숫자도 바뀐다. 같은 정수값 1~100%를 사용하며 기본은 100%다. |
| 상태이상              | 각 포켓몬          | 없음·화상·마비·독·맹독·수면·얼음 중 하나 선택. 기본은 없음. 특성이나 기술로 바뀔 때도 같은 값을 쓴다.                                                                                        |
| 비교 목적             | 각 상대            | 공격·방어·스피드 중 하나 이상 복수 선택                                                                                                                                                      |
| 날씨                  | 상대별 배틀 조건   | 없음·쾌청·비·모래바람·눈 중 하나 선택. 기본 없음                                                                                                                                             |

검색형 입력은 Enter 또는 목록 클릭으로 확정한 항목만 계산에 전달한다. 현재 HP는 어느 방식으로 편집하든 해당 퍼센트로 표시될 수 있는 가장 높은 실제 HP로 환산한다. 내 포켓몬의 현재 HP를 바꾸면 모든 상대 비교에 적용된다.

| 특성 발동                | 발동을 직접 선택하는 특성. 잠복·애널라이즈는 상대별, 나머지는 해당 포켓몬에 적용                                                   | 선택 시 기본 ON. 애널라이즈는 기본 OFF. 심록 등 HP 조건 특성을 켜도 현재 HP 입력값은 유지한다. 곡예 ON에서는 도구 입력을 비활성화하고 OFF에서는 허용한다.              |

| 확정 랭크 변화 반영      | 확정 랭크 상승·하락·초기화 효과가 있는 공격기                                                                                      | 기본 ON. 기술에 정해진 발생 시점에 반영한다. OFF면 입력한 시작 랭크를 유지한다. 확률형 변화가 발동한 상황은 기존 시작 랭크에서 지정한다.                               |
| 상대와 성별 관계         | 투쟁심 · 상대별                                                                                                                    | 같음 / 다름 중 선택. 첫 선택은 다름. 무보정 비교는 특성을 비워 둔다.                                                                                                   |
| 탈 상태                  | 탈을 선택한 따라큐                                                                                                                 | 온전함 / 깨짐 중 선택. 기본 온전함. 이미 깨진 폼은 깨진 상태로 계산한다.                                                                                               |
| 상태이상 발동 표시       | 근성·이상한비늘·속보 · 특성 보유자의 이미지 옆                                                                                     | 선택 시 기본 화상 ON. 붉은 ‘화상’을 누르면 회색으로 바뀌고 공통 상태이상이 ‘없음’이 된다. 다시 켜거나 공통 상태이상에서 다른 상태 하나를 선택할 수 있다.               |

코골기를 고르면 기존 상태이상을 수면으로 교체하고 선택 중에는 수면으로 고정한다. 기술을 바꿔도 이전 상태를 자동 복원하지 않는다. 반사 기술의 받은 데미지는 연결된 상대 기술에서 계산한다.

한 선택에 필요한 입력이 여럿이면 함께 표시한다. 예를 들어 스케일샷에는 적중 타수와 랭크 변화 반영이 모두 뜬다. 지진으로 바꾸면 두 입력을 숨기고 이전 값도 계산 요청에서 뺀다. 웹은 선택 단계에서 범위를 제한하고 공통 계산 함수는 웹·CLI가 보낸 입력을 최종 검증한다. [조건부 기술의 제품 규칙](DECISIONS.md#조건부-기술의-제품-규칙)

### 3.3 결과의 의미

- 표시 목적은 현재 세팅의 결과를 보여 주는 것이다. 입력을 바꿔도 계산 결과가 같다면 같은 결과를 표시한다.
- 공격·방어에서는 확정 또는 난수에 따른 KO 타수와 확률, 데미지 범위를 제공한다.
- 같은 KO 타수라도 확정 KO와 난수에 따른 KO를 구분할 수 있도록 타수와 확률을 함께 표시한다.
- KO 확률은 선택한 동일 기술을 N회 사용해 모두 명중했을 때, 데미지 난수에 따라 N회 이내에 상대를 쓰러뜨릴 확률이다. 명중률, 급소 발생 확률, 부가효과 발생 확률을 하나의 성공 확률로 합산하지 않는다.
- 기술 결정력은 비교 결과, 물리내구·특수내구는 포켓몬 능력치 아래에 표시하는 안을 마련했다. 정확한 공식·단위·반영할 보정은 아직 확정하지 않았다.
- 스피드는 수치의 빠름·동속·느림을 비교한다. 모든 전투 행동의 순서를 시뮬레이션하는 기능으로 확대하지 않는다.
- 결과에서 대표로 보여 줄 타수의 선택, 확률 표시 자릿수, 근사 결과의 처리와 반복 공격 시 지원할 상태 변화는 계산 입력·출력 계약에서 확정한다.

## 4. 회복 효과와 도구의 범위

- 자뭉열매, 먹다남은음식 등 회복 효과를 포함한 전투 진행 계산은 MVP에서 제외한다.
- 이후 진행한 엔진 기능 조사는 지원 가능성을 확인한 것이다. 회복 효과를 다시 MVP에 넣기로 결정한 것은 아니다.
- 도구 입력 자체는 제공한다. 도구별로 어떤 효과를 계산에 반영하는지 지원 범위를 분명하게 한다.
- 슈캐열매 등 반감열매는 첫 공격의 데미지 감소와 반복 공격 중 소모 처리를 구분해서 검증해야 한다. 현재 문서는 반복 공격의 정확한 처리가 확인되었다고 보장하지 않는다.
- 엔진에 빠진 처리를 보완할 수 있다는 가능성과, 실제 추가 구현 범위가 승인되었다는 사실을 구분한다.

## 5. 저장과 로그인

### 5.1 두 종류의 저장

| 구분                   | 저장하는 내용                                                                       | 저장 위치와 목적                                   |
| ---------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------- |
| 명시적으로 저장한 세팅 | 내 포켓몬의 세팅                                                                    | 계정에 연결해 저장하고 PC·모바일에서 불러오기      |
| 자동 복원할 작업 화면  | 편집 중인 내 세팅, 통합 상대 목록, 상대별 비교 목적과 계산 조건 등 마지막 작업 상태 | 브라우저 로컬 저장으로 같은 환경에서 작업 이어가기 |

- 로그인 제공자는 네이버를 우선 사용한다.
- 네이버 이용자 식별자로 계정을 구분하고 표시 이름은 모두 `트레이너`로 저장한다. 연락처 이메일·이름·별명·사진은 계정 생성에 사용하지 않는다.
- 로그인한 사용자가 명시적으로 저장한 내 포켓몬 세팅은 앱 사용자 ID(`user.id`)에 연결할 예정이다. 저장·불러오기 구현은 후속 작업이다. [계정과 저장 세팅의 관계](DECISIONS.md#d19-네이버-단일-로그인과-인증-데이터의-기본-구조)
- 계산 기능 전체를 로그인 뒤에만 사용할 수 있게 만드는 요구사항은 없다.
- 상대 목록이나 전체 파티를 명시적 저장 대상으로 확장하지 않는다.
- 명시적 저장은 사용자가 저장 동작을 했을 때 반영한다. 실험 중인 입력 변경이 계정에 저장한 기준 세팅을 자동으로 덮어쓰지 않는다.
- 브라우저의 작업 초안을 기기 간에 자동 동기화하는 기능은 현재 범위에 없다.

### 5.2 저장 세팅을 불러올 때

1. 사용자가 목록에서 불러올 세팅을 직접 선택한다.
2. 선택한 세팅을 현재 내 포켓몬 입력에 적용한다.
3. 통합 상대 목록과 상대별 비교 목적·계산 조건은 유지한다.
4. 적용된 현재 입력을 기준으로 결과를 갱신한다.

- 불러오기 전 입력하던 모든 포켓몬을 별도 이력으로 자동 보관하지 않는다.
- 저장 목록을 백그라운드에서 다시 조회하더라도 편집 중인 입력을 덮어쓰지 않는다.
- 작업 화면의 로컬 복원이 끝났는지 확인한 뒤 자동 저장을 시작한다. 기본 입력값이 먼저 저장되어 이전 작업을 지우는 상황을 방지한다.

## 6. 화면 방향

- PC에서는 내 포켓몬 입력과 상대별 결과를 함께 확인하고 수정할 수 있는 구성을 기본 방향으로 삼는다.
- 내 입력을 한쪽에 두고 통합 상대 목록에서 상대별로 선택한 공격·방어·스피드 결과를 함께 표시한다. 계산 영역을 전환하며 결과를 확인하는 구성을 대체한다. 세부 폭과 배치는 화면 설계에서 확인한다.
- 상대는 세팅과 비교 목적, 결과 요약을 쉽게 확인하고, 필요한 경우 상세 입력을 열 수 있게 구성한다. 필요한 비교 결과만 표시해 정보량을 조절한다.
- 모바일에서는 내 세팅 수정과 상대 결과 확인에 필요한 스크롤과 반복 동작을 줄이는 방향으로 설계한다.
- 스타일링은 Tailwind CSS를 사용한다. PC 시안은 왼쪽에 내 포켓몬의 기본 입력, 오른쪽에 상대별 결과를 정렬하고 한 상대의 상세 설정을 펼치는 구조다. 조건부 입력의 노출 위치와 모바일 배치는 후속 화면 설계에서 정한다.

### 6.1 포켓몬 이미지와 운영 방침

- 포켓몬 이미지는 [PokéAPI Sprites](https://github.com/PokeAPI/sprites)의 `other/official-artwork` 정적 PNG를 사용하는 방향으로 정했다. 이미지 연결 코드는 아직 적용하지 않았으며, 지원 포켓몬과 메가진화·리전폼의 매핑은 구현 단계에서 확인한다.
- 학습 및 정보 제공을 위한 비상업적 팬 프로젝트로 운영한다. 비상업적 목적, 포켓몬 권리자, 공식 승인·후원·제휴 관계 부재와 이미지 출처·권리 안내 링크를 표시할 예정이다. 고지 UI는 아직 적용하지 않았다.
- 이미지에 대한 개별 사용 허락은 확인되지 않았다. 비상업 운영·출처·권리자 고지를 사용 허락이나 저작권 문제 해소의 근거로 기록하지 않는다. 선택 이유와 남은 제약은 DECISIONS.md의 D16에 기록한다.

## 7. 현재 제외한 기능

## 9. MVP 확인 기준

다음은 합의한 기능에서 도출한 확인 항목이다. 아직 통과한 항목으로 기록하지 않는다.

1. 챔피언스에서 지원하기로 정한 포켓몬과 계산 조건을 입력할 수 있다.
2. 하나의 내 포켓몬 세팅과 통합 상대 목록을 사용하고, 상대마다 공격·방어·스피드 비교 목적을 하나 이상 선택·수정할 수 있다.
3. 상대를 한 마리씩 추가·수정·제거할 수 있고, 한 상대에 여러 목적을 선택하면 같은 상대 세팅으로 계산한다. 최대 상대 수는 확정 후 제한과 검증 기준에 반영한다.
4. 현재 입력 변경이 선택한 모든 비교 결과에 반영되고 한 화면에서 함께 확인된다. 데미지 범위와 KO 타수·확률을 정의한 의미대로 표시한다.
5. 합의한 공식으로 결정력·내구 지표와 스피드 실수치를 표시한다.
6. 회복 효과 제외 등 계산의 지원 범위가 결과 해석과 일치한다.
7. 네이버 로그인과 내 세팅의 계정 저장·불러오기가 동작한다.
8. 로컬 작업 복원, 저장 세팅 불러오기와 서버 데이터 갱신이 합의한 입력 유지 규칙을 지킨다.
9. PC와 모바일에서 주요 입력·계산·저장 흐름을 사용할 수 있다.
10. 대표 계산 사례와 핵심 사용자 흐름을 검증하고, 실제 측정 결과를 개선의 기준으로 남긴다.

첫 배포 플랫폼, 일정, 구체적인 성능 목표 수치는 아직 정하지 않았다. 숫자를 임의로 완료 조건에 추가하지 않는다.

#### 개발 서버 실행과 기본 검사

저장소 루트에서 실행한다. 새 환경에는 fnm 등으로 `.node-version`의 Node.js `26.13.1`과 루트 `package.json`의 pnpm `12.19.0`을 먼저 준비한다.

| 명령                             | 용도                                                                                     |
| -------------------------------- | ---------------------------------------------------------------------------------------- |
| `pnpm install --frozen-lockfile` | 고정한 의존성을 설치한다.                                                                |
| `pnpm dev`                       | 개발 서버를 실행한다. 기본 주소는 `http://localhost:3000`이다.                           |
| `pnpm format:check`              | 파일을 수정하지 않고 서식을 검사한다.                                                    |
| `pnpm lint`                      | 웹·계산 패키지의 린트를 검사한다. 경고도 실패로 처리한다.                                |
| `pnpm typecheck`                 | 두 패키지의 타입을 검사한다. 웹은 `next typegen`으로 필요한 라우트 타입을 먼저 생성한다. |
| `pnpm build` · `pnpm start`      | 웹 프로덕션 빌드를 만든 뒤 해당 서버를 실행한다.                                         |

### 로컬 PostgreSQL 구성

[인증 작업 #7](https://github.com/nickwildee/champsparty/issues/7) 중 [#8](https://github.com/nickwildee/champsparty/issues/8)에서 Homebrew PostgreSQL `18.7`을 구성했다. 데이터 디렉터리는 `/opt/homebrew/var/postgresql@18`, 포트는 `5432`, Unix 소켓은 `/tmp`다. macOS 로그인 시 자동 실행은 등록하지 않았다.

- 앱은 `apps/web/.env.local`의 `DATABASE_URL`로 `champsparty_app`에 접속한다. 이 역할은 `public`의 서비스 데이터를 읽고 쓴다.
- 마이그레이션은 `apps/web/.env.migrations.local`의 `MIGRATION_DATABASE_URL`로 `champsparty_migrator`에 접속한다. 이 역할이 DB `champsparty`와 `public`·`drizzle` 스키마를 소유하고 구조를 변경한다. 두 역할은 서로 다른 비밀번호를 사용하며 실제 환경 파일은 권한 `0600`으로 Git에서 제외한다.
- 두 프로젝트 역할에 IPv4·IPv6·Unix 소켓에서 SCRAM 비밀번호 인증을 적용했다. 이 설정을 적용하기 전의 HBA 파일은 `/opt/homebrew/var/postgresql@18/pg_hba.conf.champsparty-before-scram`에 있다. 당시 정상·오류·누락 비밀번호와 권한을 포함한 직접 검사 40건을 확인했다. 세부 권한과 기존 관리 역할의 로컬 `trust` 예외는 [D17](DECISIONS.md#d17-로컬-postgresql과-서비스마이그레이션-역할-분리)에 있다.

| 명령                                                                                                      | 용도                                                             |
| --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `brew services run postgresql@18`                                                                         | 필요할 때 실행. 로그인 시 자동 실행은 등록하지 않음              |
| `brew services stop postgresql@18`                                                                        | 서버 중지                                                        |
| `brew services info postgresql@18 --json`                                                                 | 실행 상태와 자동 실행 등록 여부 확인                             |
| `/opt/homebrew/opt/postgresql@18/bin/pg_isready -h 127.0.0.1 -p 5432`                                     | 서버의 접속 수락 상태 확인. 계정 인증 검증과는 별개              |
| `/opt/homebrew/opt/postgresql@18/bin/psql -h 127.0.0.1 -p 5432 -U champsparty_app -d champsparty -W`      | 앱 역할로 접속. 비밀번호는 명령 인자가 아닌 숨겨진 입력으로 전달 |
| `/opt/homebrew/opt/postgresql@18/bin/psql -h 127.0.0.1 -p 5432 -U champsparty_migrator -d champsparty -W` | 구조 변경 역할로 접속                                            |

접속 후 `SELECT current_database(), current_user, version();`과 `SELECT 1;`로 대상 DB·역할·버전과 쿼리 실행을 확인한다. `pg_isready`는 서버의 접속 수락만 확인한다.

### pg·Drizzle 연결 — #9, 구현·검증 완료

앱은 서버 전용 모듈에서 pg 풀을 재사용한다. 로컬 풀당 최대 연결은 10개, 연결 획득 대기는 5초, 유휴 정리는 10초다. 개발 모드에서는 풀을 `globalThis`에 보관하므로 접속 정보나 풀 설정을 바꾸면 개발 서버를 재시작한다. DB 기능을 처음 호출할 때 설정 누락을 확인한다.

루트 `pnpm db:check`는 macOS 셸에서 `@next/env`로 앱 개발 환경을 읽고 같은 연결 코드로 읽기 쿼리와 `champsparty`·`champsparty_app`을 확인한 뒤 풀을 닫는다. 종료 코드 0은 성공, 1은 실패다. 실제 DB·Next.js에서 성공·오류 응답과 서버 전용 경계를 확인했다. 재현 조건, 설치 버전, 임시 시나리오 7개의 범위와 한계는 [D18](DECISIONS.md#d18-앱-db-연결과-검증-방식)에 있다.

### Better Auth와 인증 테이블 — #10

웹 서버는 `apps/web/.env.local`의 앱 역할 `DATABASE_URL`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`을 사용한다. 주소에는 프로토콜·호스트와 필요한 포트를 적고, 비밀값은 무작위 32바이트를 Base64로 인코딩해 준비한다. 세션은 DB에 저장하며 만료 7일·갱신 간격 1일이다.

인증 스키마 변경 시 저장소 루트에서 다음 명령으로 TypeScript 스키마와 스냅샷 차이에 대한 SQL을 차례로 생성한다.

```sh
pnpm --filter @champsparty/web exec auth generate --config auth-schema.config.ts --adapter drizzle --dialect postgresql --output src/server/auth-schema.ts
pnpm --filter @champsparty/web exec drizzle-kit generate --config drizzle.config.ts
```

생성한 차이를 검토한 뒤 `pnpm db:migrate`로 로컬 DB에 적용한다. 서비스 테이블은 `public`의 `user`·`account`·`session`·`verification`, 적용 이력은 `drizzle.__drizzle_migrations`에 저장된다. [#10](https://github.com/nickwildee/champsparty/issues/10)에서는 인증 테이블 접근, 재적용 후 같은 SQL의 이력 1건, 쿠키 없는 세션 조회(200·`null`)와 로그아웃(200)을 확인했다. 쿠키 설정·수집 항목과 검증 근거는 [D20](DECISIONS.md#d20-better-auth-기반-인증-테이블과-세션-설정)에, 배포 후 IP 확인·요청 제한 검토는 [#21](https://github.com/nickwildee/champsparty/issues/21)에 있다.

### 네이버 로그인 시작 — #11

네이버 개발자센터에 등록한 로컬 서비스 URL은 `http://localhost:3000`, 콜백은 `http://localhost:3000/api/auth/callback/naver`다. 기본 이용자 식별자만 사용하도록 필수·추가 프로필 항목은 모두 비워 둔다. 앱의 `BETTER_AUTH_URL`을 등록한 서비스 주소에 맞추고 `.env.local`에 `NAVER_CLIENT_ID`와 `NAVER_CLIENT_SECRET`을 넣은 뒤 서버를 재시작한다. 두 값이 모두 있으면 네이버 로그인이 활성화된다. 키가 없어도 세션 조회와 로그아웃을 사용할 수 있다.

당시 로컬 프로덕션 빌드에서 `POST /api/auth/sign-in/social`이 HTTP 200과 네이버 인증 URL을 반환했다. 콜백 주소 일치, 기본 요청에 `scope`가 없는 것까지 확인했다. 실제 동의·콜백·로그인한 세션은 #13에서 확인한다. [네이버 식별자 및 검증 범위 D21](DECISIONS.md#d21-네이버-이용자-식별자와-내부용-이메일)

### 기반 실행 환경의 검증과 한계

- 초기 저장소·세 인계 문서의 배치와 LF·제외 경로 검사는 [D12](DECISIONS.md#d12-초기-저장소-설정과-문서-구성)에 기록했다. fnm이 샌드박스에서 멀티셸 링크를 만들지 못한 조건과 당시 새 로그인 셸의 실제 버전은 [D13](DECISIONS.md#d13-개발-도구-버전과-최소-워크스페이스-설정)에 있다.
- 초기 워크스페이스는 고정 설치, 서식·peer·타입·린트 검사, 프로덕션 빌드와 브라우저에서의 내부 패키지 호출을 확인했다. Turbopack이 내부 포트를 열지 못했던 실행 환경과 동일 명령의 재검증 조건은 [D14](DECISIONS.md#d14-두-패키지-연결과-최소-nextjs-실행-환경)에 있다.
- [CI 워크플로](../.github/workflows/ci.yml)는 Ubuntu에서 저장소에 지정한 Node.js·pnpm으로 고정 설치 → 서식 → 린트 → 타입 검사 → 웹 빌드를 실행한다. 실행 로그와 검증 경계는 [D22](DECISIONS.md#d22-github-actions-기본-검사)에 있다.

## 11. 문서 유지

기능 범위나 현재 상태가 바뀌면 해당 작업의 기준과 검증 범위를 갱신한다. 주요 선택과 변경 이유는 [결정 기록](DECISIONS.md)에 남긴다.

- 0.20에서는 `main`의 현재 동작·미검증 범위·다음 과제를 앞에 모으고 작업별 실행 명령과 협업 지침 적용 이력을 연결했다.

- 인증 작업 0.10~0.14에서는 로컬 PostgreSQL, 앱 연결, 인증 테이블·세션, CI, 네이버 로그인 시작 요청을 순서대로 기록했다. 계산기 브랜치 0.12~0.15에서는 싱글 검증 화면·카탈로그·통합 상대 목록을 정리하고 일회성 코드를 CLI로 교체했다. 2026-11-24에 제품 데이터·과거 조사·조건부 규칙의 위치를 구분했다.
- 0.2~0.4에서는 저장소·워크스페이스 초기 설정과 검증 근거를 정리했다. 0.7에서는 이미지 출처·권리와 남은 제약을 기록했다.
