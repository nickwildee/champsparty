## D01. 숙련자의 세팅 조정을 위한 현재 결과 표시

- **배경:** 사용자는 이미 실전 포켓몬을 다룰 수 있다. 직접 정한 여러 상대에 대한 가능성을 한눈에 보고 싶어 한다.
- **합의:** 현재 입력의 스피드, 데미지 범위, KO 타수·확률, 결정력·내구를 제공한다.
- **사용자 수정:** 변경 전후를 비교할 필요가 있는지에 대해, 현재 능력치에서 어떤 결과가 나오는지만 보여 주는 것이 목적이라고 명확히 했다.
- **검토했던 대안:** 변경 전후 비교, 변화 알림, 파티 취약점 분석과 추천.
- **선택 이유:** 사용자가 판단할 수 있는 계산 정보를 제공하고 입력·확인 동선을 단순하게 유지한다.
- **범위:** 비교 이력, 자동 추천과 취약점 보고서를 현재 MVP에 포함하지 않는다.

## D02. 챔피언스만 지원하고 기존 계산 엔진 활용

- **배경:** 사용자는 직접 구현의 주된 부담을 많은 데이터의 재입력으로 보았다. 지원 게임을 챔피언스로 제한하면 직접 구현도 가능하지 않은지 검토했다.
- **합의:** `@smogon/calc`를 활용한다. 직접 계산 엔진 전체를 새로 만드는 방향은 채택하지 않는다.
- **사용자 선택:** 참고 서비스가 같은 계열의 엔진을 사용한다는 논의 이후, 기존 엔진을 가져다 쓰는 방향으로 변경했다.
- **대안:** 챔피언스 전용 엔진 직접 구현, 여러 게임을 지원하는 범용 계산기 구성.
- **선택 이유:** 기존 계산 로직과 데이터를 활용하고, 이 프로젝트의 핵심인 다수 상대 입력·즉시 갱신·저장 경험에 집중한다.
- **검증 필요:** 실제 설치할 배포 버전의 챔피언스 지원, 데이터 범위, 능력치 입력 변환과 난수 결과. 저장소 소스에서 지원 코드가 보인다는 사실만으로 설치 버전까지 검증한 것으로 쓰지 않는다.

## D03. 회복 효과는 제외하고 도구별 지원을 구분

- **초기 아이디어:** 자뭉열매와 먹다남은음식 같은 회복을 고려한 KO 타수 계산.
- **변경된 합의:** 회복 효과를 포함한 전투 진행 계산은 MVP에서 제외한다. 포켓몬별로 시작 랭크와 현재 HP를 입력한다. HP 슬라이더의 범위는 0~100%, 기본값은 100%다.
- **사용자 이유:** 파티 준비를 위한 계산기에 전투 내부의 변수를 지나치게 넣으면 제공할 정보와 범위가 커진다고 판단했다.
- **이후 논의:** 엔진의 회복 및 반감열매 지원 여부와, 부족한 처리의 추가 구현 가능성을 확인했다.
- **현재 기준:** 가능성 조사가 회복 기능의 재도입 승인을 뜻하지 않는다. 반감열매의 첫 타 감소와 반복 공격 중 소비는 별도로 검증한다.
- **확률의 의미:** 동일 기술을 N회 사용해 모두 명중했을 때 N회 이내에 쓰러뜨릴 확률로 해석한다. 앞서 합의한 이 의미는 유지하며, 이후 철회된 회복 반영은 제외한다.
- **검증 필요:** 정확한 KO 확률이 성립하는 입력 범위와 엔진의 정밀도. 추가 보완이 필요하면 범위와 방법을 먼저 논의한다.

## D04. 공통 내 세팅과 통합 상대 목록, 상대별 비교 목적

- **초기 방향:** 내 포켓몬 세팅은 공유하되 스피드·공격·방어별 상대 목록을 따로 두고, 각 목록에 상대를 0~5마리까지 추가하며 계산 영역을 전환해 결과를 확인하도록 했다.
- **변경 배경(2026-11-17):** 능력치를 배분할 때 특정 공격을 버틸 수 있는지, 필요한 상대보다 빠른지, 공격 포인트를 줄여도 KO 타수·확률이 유지되는지를 함께 판단해야 한다. 영역별로 분리된 목록과 화면 전환은 서로 다른 목적의 결과를 오가며 확인하게 하고, 같은 상대 세팅의 중복 입력을 요구할 수 있다.
- **현재 합의:** 하나의 내 포켓몬 세팅과 통합 상대 목록을 사용한다. 상대마다 공격·방어·스피드 비교 목적을 하나 이상 선택하고, 여러 목적을 함께 지정할 수 있다. 한 상대의 여러 비교는 같은 상대 세팅을 공유하며, 내 입력을 수정하면 선택한 모든 비교 결과를 한 화면에서 갱신한다.
- **대안:** 영역별 목록을 유지하고 결과만 한 화면에 모으는 최소안은 기존 구성을 적게 바꿀 수 있지만, 같은 상대 세팅을 목적별로 반복 입력할 수 있다. 상대 목록과 비교 목적을 함께 통합하는 방향을 선택했다.
- **선택 이유:** 사용자가 직접 능력치를 조정하면서 공격 성능·생존 가능성·스피드를 함께 확인하도록 하고, 같은 상대에 대한 반복 입력과 결과 확인을 위한 화면 전환을 줄이는 구조다. 동선과 사용성 개선의 실제 효과는 구현 후 검증한다.
- **입력과 표시:** 상대는 필요한 만큼 한 마리씩 추가·수정·제거한다. 상대별로 선택한 목적에 필요한 입력과 결과를 제공하고, 상세 입력을 접어 결과 요약을 우선 확인할 수 있게 한다. KO 결과는 타수와 확률을 함께 표시한다.
- **저장·복원:** 브라우저의 작업 복원 대상에 통합 상대 목록과 상대별 비교 목적·계산 조건을 포함한다. 계정에 저장한 내 세팅을 불러올 때 이 상대 목록과 목적·조건을 유지한다. 상대 목록의 명시적 계정 저장은 추가하지 않는다.
- **감수할 점:** 상대별 다중 목적에 따른 입력 폼과 결과 배치를 설계해야 한다. PC와 모바일에서 정보량·스크롤과 입력 응답성을 확인해야 한다.
- **미정·범위:** 기존 영역별 5마리 제한을 통합 목록의 상한으로 그대로 적용하지 않으며, 통합 목록의 최대 상대 수는 별도로 확정한다. 자동 능력치 배분 추천, 변경 전후 비교와 자동 이력은 MVP에 추가하지 않는다.
- **화면 방향:** PC에서 왼쪽에는 내 포켓몬 기본 입력, 오른쪽에는 상대별 공격·방어·스피드 결과를 둔다. 상세 설정은 선택한 상대만 펼친다. 상대별 필드는 양쪽 벽을 분리한 뒤 같은 상대의 세 비교에서 공유한다.
- **검증 상태:** 기본 입력과 펼침 상태를 PC 시안에서 확인할 수 있다. 전체 UI와 계산 동작은 구현·검증 전이다. 상대·비교 목적의 추가·수정·제거, 한 상대의 여러 목적 간 세팅 공유, 내 입력 변경 시 모든 선택 결과의 갱신, 저장본 불러오기·로컬 복원과 PC·모바일 주요 흐름을 검증한다.

## D05. 기준 세팅 저장과 작업 화면 복원을 분리

- **배경:** 사용자는 내 포켓몬 세팅을 저장하고 나중에 불러와 조정하고 싶어 한다. 마지막 입력을 복원하는 편의도 함께 검토했다.
- **합의:** 내 포켓몬 세팅은 명시적으로 계정에 저장한다. 편집 중인 내 세팅, 통합 상대 목록과 상대별 비교 목적·계산 조건을 포함한 작업 화면은 브라우저 로컬에서 자동 복원한다.
- **대안:** 모든 입력을 계정에 자동 저장하거나 전체 작업 화면을 명시적 저장 단위로 삼는 방식.
- **선택 이유:** 저장한 기준 세팅과 실험 중인 입력을 구분하면서 반복 입력 부담을 줄인다. 계정 저장본은 기기를 바꾸어 불러올 수 있다.
- **불러오기 규칙:** 사용자가 선택한 저장 세팅으로 내 입력을 교체하되 통합 상대 목록과 상대별 비교 목적·계산 조건은 유지한다. 이전 입력을 모두 별도 이력으로 보관하지 않는다.
- **범위:** 작업 초안의 기기 간 자동 동기화와 전체 파티·상대 목록의 계정 저장은 추가하지 않는다.

## D06. 편집 중인 입력을 서버 갱신으로 덮어쓰지 않음

- **논의의 핵심:** 저장한 한카리아스 세팅을 불러와 수정하는 중에 저장 목록이 다시 조회되더라도, 현재 편집값이 원래 저장값으로 돌아가면 안 된다.
- **합의:** 저장 데이터를 조회하는 상태와 계산기에 적용한 작업 입력을 분리한다. 명시적 불러오기에서만 저장 데이터를 작업 입력에 적용한다.
- **갱신 방향:** 목록을 열거나 저장·수정·삭제 결과를 반영하는 등 필요한 시점에 서버 데이터를 갱신한다. 노력치 입력 변경을 서버 재조회와 연결하지 않는다.
- **복원 규칙:** 이전 로컬 작업을 확인·복원한 뒤 자동 저장을 시작한다.
- **검증할 흐름:** 불러오기 후 수정 → 서버 목록 갱신 → 입력 유지, 새로 열기 → 기존 초안 복원 → 이후 변경 저장.
- **미정:** Query의 구체적인 캐시 시간과 재조회 옵션, 로컬 저장 형식과 갱신 방식.

## D07. 작은 풀스택 모노레포로 시작

- **합의:** Next.js + TypeScript를 사용하고, 웹과 서버 기능을 한 Next.js 애플리케이션에서 제공한다. 계산 로직은 별도 패키지로 분리한다.
- **현재 구성 방향:** `apps/web`, `packages/calculator`와 pnpm 워크스페이스. 아직 실제 폴더나 패키지 생성이 완료되었다는 뜻은 아니다.
- **대안:** 처음부터 독립 API 서버를 두거나 여러 공유 패키지와 추가 모노레포 도구를 함께 도입하는 방식.
- **선택 이유:** 현재 서버의 핵심 역할은 인증과 개인 세팅 저장이다. 지금 필요한 경계부터 두고 운영·개발 구성을 작게 유지한다.
- **사용자 기준:** 실제 필요가 생겼을 때 사용하고, 이후 필요한 경우 마이그레이션한다는 방향에 동의했다.
- **재검토 조건:** 서버의 독립 배포 등 구체적인 요구가 생겼을 때 분리를 검토한다. 나중에 쓸 수도 있다는 이유만으로 구조를 미리 늘리지 않는다.

## D08. 계산은 브라우저, 계산 패키지는 입력과 출력에 집중

- **구현 방향:** 현재 입력을 계산 엔진이 받을 형태로 변환하고, 결과를 화면에서 사용할 형태로 정리하는 계산 로직을 `packages/calculator`에 둔다. 계산은 브라우저에서 수행한다.
- **대안:** 입력을 바꿀 때마다 서버에 계산 요청을 보내는 방식.
- **선택 이유:** 실시간 조정에 필요한 계산을 네트워크 왕복과 분리하고, 계산 로직을 화면 코드와 별도로 검증한다.
- **경계:** 계산 패키지는 UI, 인증, DB 연결과 로컬 저장을 직접 관리하지 않는다.
- **감수할 점:** 브라우저로 전달되는 데이터·코드 크기와 모바일의 계산 응답성을 실제로 확인해야 한다.
- **검증과 개선:** 입력 반응, 계산 시간과 초기 로딩을 측정한 뒤 필요하면 최적화한다. Worker나 추가 캐시를 처음부터 필수로 정하지 않는다.

## D09. 작업 상태와 서버 상태를 목적에 맞게 관리

- **구현 방향:** 계산기 작업 입력은 React `useReducer`, 작은 UI 상태는 필요에 따라 `useState`, 저장된 서버 세팅은 TanStack Query로 관리한다.
- **계산 결과:** 현재 입력으로부터 파생한다. 입력과 별도로 수정 가능한 중복 결과 상태를 기본 구조로 두지 않는다.
- **대안:** 모든 입력을 개별 `useState`로 관리하거나 Zustand 같은 외부 상태 관리 도구를 사용하는 방식.
- **선택 이유:** 내 세팅 수정, 상대 추가·수정·삭제, 저장본 적용 등의 변경을 액션으로 모으고, 서버 데이터의 조회·갱신 상태는 별도로 다룬다.
- **주의할 해석:** `useReducer`를 선택했다고 렌더링 성능이 자동으로 개선되는 것은 아니다. 상태 공유나 구독 요구가 달라지면 다른 도구도 검토할 수 있다.
- **검증 필요:** 상태 변경 흐름, 계산 갱신, 복원 순서와 서버 갱신 중 입력 유지.

## D10. 계정 저장에 PostgreSQL·Drizzle, 로그인은 네이버

- **현재 구현 방향:** PostgreSQL과 Drizzle을 사용하고, 네이버 로그인을 Better Auth로 연동하는 방향으로 논의했다.
- **대안:** 다른 ORM, 초기 후보였던 카카오 로그인, 인증 흐름을 직접 구성하는 방식.
- **선택 이유:** 사용자와 저장 세팅의 관계를 DB에 두고, TypeScript에서 스키마와 쿼리를 다루는 구성을 사용한다. 인증의 반복 작업은 라이브러리를 활용하는 방향이다.
- **범위:** 게임의 모든 계산 데이터를 DB에 다시 입력하는 것이 목적은 아니다. 계정에 저장할 사용자 세팅이 중심이다.
- **현재 상태:** 로컬 PostgreSQL 설치와 두 역할의 직접 접속·권한 검증을 마쳤다. 구체적인 구성과 대안은 D17에, 앱의 pg·Drizzle 공통 연결 구현·검증은 D18에 기록한다.
- **검증 필요:** 인증 라이브러리 버전 호환성, 실제 네이버 로그인과 세션, 사용자별 저장 데이터 접근 제어.
- **미정:** 배포용 DB 제공 서비스, 상세 인증 스키마와 인증 설정. 네이버 로그인 선택을 특정 OAuth/OIDC 연동 방식의 실행 검증 완료로 쓰지 않는다. n3r 도입은 선택하지 않았다.

## D11. 생산성 중심 MVP 이후 실제 측정으로 개선

## D13. 개발 도구 버전과 최소 워크스페이스 설정

- **문제:** 초기 셸은 Homebrew의 Node.js `23.7.0`과 기존 전역 pnpm `10.18.1`을 사용했다. 프로젝트에서 사용할 버전을 명시하고 다른 환경에서도 맞출 기준이 필요했다.
- **합의:** fnm으로 Node.js를 관리하고 Node.js `26.13.1`(26 LTS), pnpm `12.19.0`을 사용한다.
- **대안과 이유:** 기존 Homebrew Node.js를 그대로 쓰거나 전역 버전만 교체할 수 있지만, 프로젝트별 전환과 버전 명시를 위해 fnm과 `.node-version`을 선택했다. 기존 pnpm 10 유지도 가능하나 새 프로젝트의 기준을 pnpm 12로 맞추기로 했다. 선택한 버전에서 애플리케이션 호환성 검증이 끝났다는 뜻은 아니다.
- **반영 범위:** `.node-version`에 정확한 Node.js 버전, 루트 `package.json`에 `private: true`·Node.js 허용 범위·정확한 `packageManager`, `pnpm-workspace.yaml`에 `apps/*`와 `packages/*`를 기록한다.
- **감수·보류:** 새 환경에서는 해당 도구 설치가 필요하다. Next.js 생성, 린터·포매터, 앱과 계산 패키지, 의존성 설치는 이번 범위에 넣지 않는다.
- **설치와 오류 해결:** fnm `1.39.0`, Node.js `26.13.1`, pnpm `12.19.0`을 설치했다. 최초 Homebrew 설치는 샌드박스의 경로 쓰기 제한으로 실패했다. `.zshrc`의 마지막 줄바꿈 부재로 붙었던 PATH 설정과 fnm 연결문은 별도 줄로 분리했다. fnm 연결문은 `eval "$(fnm env --use-on-cd --shell zsh)"`다. pnpm 설치 중 스크립트 허용 정책 경고는 실행 실패가 아니었다.
- **정적·제한된 환경 검증:** JSON·버전 값, YAML 구문·경로, LF, 내부 문서 링크와 `git diff --check`를 확인했다. 초기 검증에서는 샌드박스가 fnm 멀티셸 링크 생성을 막아 새 셸 자동 전환을 검증하지 못했다. 대신 설치된 Node.js의 bin 경로를 검증 프로세스의 PATH에만 지정해 Node.js `v26.13.1`, npm `11.20.0`, pnpm `12.19.0` 실행과 `pnpm -r list --depth -1`, `pnpm --filter champsparty list --depth -1`의 루트 인식을 확인했다. 영구 PATH 설정은 변경하지 않았다.
- **새 셸 검증(2026-11-17):** 샌드박스 안의 로그인·대화형 zsh에서는 fnm 멀티셸 링크 생성이 `Operation not permitted`로 막혀 실제 `node`가 Homebrew의 `v24.22.1`을 가리켰다. 권한 제한 밖에서 같은 방식으로 실행하자 `fnm current`와 `node --version`은 `v26.13.1`, npm은 `11.20.0`, pnpm은 `12.19.0`이었다. `node`와 `pnpm`은 fnm 멀티셸 경로에서 실행됐고 `pnpm -r list --depth -1`이 비공개 `champsparty` 루트를 인식했다. 새 셸 자동 전환과 최소 워크스페이스 실행의 완료 기준을 충족했다.
- **잠금 파일:** 이 단계의 `pnpm-lock.yaml`에는 pnpm 자체 버전 관리 항목만 있으며 앱 의존성은 아직 포함하지 않았다.
- **남은 검증:** 앱·계산 패키지 생성, 의존성 설치, 실행·빌드, 계산·인증·DB 연동은 별도 단계다. Next.js 생성 옵션, 린터·포매터와 스타일링 구성은 다음 단계에서 논의한다.
- **확인 자료:** [Node.js 26.13.1 LTS 배포](https://nodejs.org/en/blog/release/v26.13.1), [pnpm 12.19.0 배포](https://pnpm.io/blog/releases/12.19.0), [fnm 설치와 셸 설정](https://github.com/Schniz/fnm#installation).

## D14. 두 패키지 연결과 최소 Next.js 실행 환경

- **문제와 범위:** 웹과 독립 계산 패키지를 실제 워크스페이스 구성원으로 연결하고 개발·검사·빌드 명령을 마련한다. 실제 포켓몬 계산, 로그인과 DB 연결은 후속 설계로 남긴다.
- **브랜치와 선행 작업:** 문서 PR #2는 `89a96e8`, 개발 도구 PR #3은 `aea96d0`으로 `main`에 병합했다. #3은 문서 병합 후 자체 커밋만 최신 `main`에 재배치해 검토 범위를 유지했다. 이슈 #4의 구현은 최신 `main`에서 만든 `codex/4-next-workspace`에서 진행한다.
- **등록과 의존성:** 루트의 `apps/*`·`packages/*` 등록을 유지하고 `@champsparty/web`, `@champsparty/calculator`를 구성했다. 웹의 `dependencies`에 계산 패키지를 `workspace:*`로 선언한다. 필요한 도구는 실행하는 패키지에 선언하며, 전체 저장소 서식을 다루는 Prettier는 루트에 둔다.
- **계산 패키지 공개 방식:** `exports`로 `src/index.ts`의 TypeScript 원본을 공개한다. 현재 Next.js가 워크스페이스 소스를 변환하므로 별도 계산 패키지 빌드·변경 감시나 `transpilePackages` 설정을 추가하지 않았다. 대안인 JavaScript·타입 선언 파일 사전 빌드는 독립 배포와 여러 소비 환경에 유리하지만, 현재 소비자는 웹 하나여서 원본 공개가 단순하다. 소비자가 TypeScript 변환 기능을 제공해야 한다는 제약을 감수한다.
- **계산 경계:** 계산 패키지는 React·Next.js·DOM·Node.js 전역 타입을 요구하지 않도록 자체 TypeScript 설정을 둔다. 연결 확인용 `add` 함수만 제공하며 실제 계산 API는 확정하지 않는다. 웹의 작은 Client Component가 버튼 이벤트에서 이 함수를 호출해 브라우저 실행을 확인한다. 페이지의 서버 렌더링 성공만으로 브라우저 계산을 검증했다고 판단하지 않는다.
- **Next.js 옵션:** Next.js `16.4.6`, React·React DOM `19.3.0`, App Router, TypeScript, `src/`, 웹 내부 별칭 `@/*`, 기본 Turbopack을 사용한다. 생성 도구의 옵션을 명시하고 설치를 건너뛴 뒤 두 패키지를 준비해 루트에서 설치했다. React Compiler와 Cache Components는 현재 요구에 필요하지 않아 활성화하지 않았다. 생성 도구가 만든 웹 내부 워크스페이스·중복 README·별도 gitignore를 제거하고 루트에서 관리한다.
- **지침 파일 자동 생성:** `--no-agents-md`는 초기 생성만 제어하며 `next dev`는 별도로 지침 파일을 만들었다. 설치 버전에 포함된 공식 설명을 확인해 `agentRules: false`로 자동 생성을 끄고 기존 루트 AGENTS.md를 사용한다. 임의로 공통 협업 지침을 추가하지 않는다.
- **스타일링:** Tailwind `4.3.3`과 공식 PostCSS 연동을 사용한다.
- **서식과 린트:** 루트에 Prettier `3.10.1`과 `format`·`format:check`를 구성했다. 각 ESLint 설정에 `eslint-config-prettier`를 적용하고 린트와 서식 검사는 별도로 실행한다. Git hook·별도 공통 설정 패키지는 추가하지 않는다.
- **검사 도구의 호환성:** 타입 검사는 TypeScript `5.9.3`을 두 패키지에서 사용한다. 최신 TypeScript `7.0.2`와 달리 현재 typescript-eslint `8.73.0`의 지원 범위는 `<6.1.0`이므로 호환되는 5.9 계열을 선택했다. 생성 도구의 ESLint 9는 설치 중 지원 종료 경고가 나와, Next.js 16.4에서 공식 지원하는 ESLint `10.15.0`을 사용한다. `eslint-plugin-import@2.32.0`, `eslint-plugin-jsx-a11y@6.10.2`, `eslint-plugin-react@7.37.5`의 peer 선언에는 10이 빠져 있어 이 세 버전에만 pnpm `overrides`의 `:peer` 선택자로 `^9 || ^10`을 지정했다. 실제 린트를 통과했으며 각 플러그인의 선언이 갱신되면 해당 보정을 제거한다. 모든 플러그인 기능을 별도로 재현한 검증은 아니다.
- **설치 기록:** pnpm `12.19.0`이 선택한 typescript-eslint `8.73.0` 계열의 최근 배포 버전에 대해 자동 추가한 정확한 버전의 `minimumReleaseAgeExclude` 항목을 유지했다. 전체 패키지의 출시 대기 시간을 끄는 설정은 사용하지 않는다. 실제 의존성과 로컬 연결은 루트 lockfile에 기록하며 생성된 코드·검사 캐시는 추적하지 않는다.
- **실제 검증:** pnpm이 루트와 두 패키지를 인식하고, 웹이 계산 패키지를 로컬 링크로 참조한다. 두 패키지의 타입 검사와 린트, 서식 검사, peer 의존성 검사, 고정 lockfile 설치와 웹 프로덕션 빌드를 통과했다. 프로덕션 HTTP 200, 개발·프로덕션 브라우저 버튼 동작, Tailwind 스타일 적용과 브라우저 경고·오류 부재를 확인했다.
- **실행 환경의 제한:** 샌드박스 안의 빌드는 Turbopack의 내부 포트 생성이 `Operation not permitted`로 막혔다. 최초 실패의 `.next` 캐시를 비운 뒤 권한 제한 밖에서 동일한 `pnpm build`가 통과했다. 개발·프로덕션 서버도 포트 사용이 가능한 환경에서 검증했다. 이 제약을 해결하기 위해 번들러나 기능 범위를 변경하지 않았다.
- **남은 작업:** `add`는 연결 확인용이다. `@smogon/calc`의 실제 챔피언스 지원·계산 계약·성능, 화면 설계, 인증·DB·저장은 다음 단계에서 각각 논의·검증한다.

## D15. 챔피언스 데미지 엔진의 설치와 싱글 검증 계약

- **문제와 범위:** 실제 배포 패키지로 챔피언스 규칙과 대표 데미지를 계산하고, 조건 변경 및 브라우저 실행을 검증한다. 통합 상대 목록을 갖춘 전체 계산기 UI의 구현은 후속 단계다.
- **설치:** `packages/calculator`의 런타임 의존성으로 `@smogon/calc` `0.12.0`을 정확한 버전으로 고정하고 lockfile에 반영했다. npm 레지스트리의 배포 버전과 설치본의 `dist`·소스·타입을 확인했다.
- **규칙과 입력:** `Generations.get(0)`을 모든 포켓몬·기술·계산 호출에 사용한다. 레벨 50과 챔피언스 능력치 공식을 사용하며, `statPoints`를 엔진의 `evs`로 그대로 전달한다. 기존 작품의 노력치로 환산하지 않는다. 각 능력치의 포인트는 0~32 정수, 합계는 최대 66, 랭크는 -6~6 정수로 검증한다. 특성은 명시적으로 전달해 기본 특성이 묵시적으로 선택되지 않게 한다.
- **현재 계약:** 싱글과 지진을 지원한다. 날씨는 없음·쾌청·비·모래바람·눈, 지형은 없음·일렉트릭·그래스·사이코·미스트, 방어 측 벽은 없음·리플렉터·빛의장막·오로라베일 중 하나를 선택한다. 도구는 없음·생명의구슬·달인의띠·부드러운모래·메타그로스나이트로 제한한다. 웹은 한카리아스와 메가 메타그로스를 고정하고 공격자의 조건과 필드만 변경한다. 방어자는 메타그로스나이트를 유지한다.
- **도구 범위의 근거:** 설치본의 챔피언스 도구 목록과 계산 코드를 함께 확인했다. 구애머리띠는 이 목록에 없으며 공격 보정도 적용되지 않아 지원하지 않는다. 생명의구슬·달인의띠·부드러운모래는 실제 출력과 보정 산술을 대조했다. 다른 도구를 이름만 전달해 지원하는 것으로 표시하지 않는다.
- **KO의 의미:** 시작 HP 100%, 기술이 모두 명중하고 동일 조건의 공격 데미지만 반복해서 누적하는 경우다. 날씨·필드는 한 번의 데미지 계산에 반영한 뒤, KO 질의 전에 엔진 결과의 날씨·지형을 비워 턴 종료 데미지와 그래스필드 회복을 제외한다. 입력 객체는 변경하지 않는다. 생명의구슬 반동에 따른 공격자 기절은 시뮬레이션하지 않는다.
- **출력과 선택 이유:** 엔진의 난수 배열·범위·KO 수치를 구조화하고 화면은 현재 입력으로부터 결과를 파생한다. 난수 배열은 같은 값도 제거하지 않는다. 퍼센트는 데미지/최대 HP로 계산해 소수 첫째 자리까지 반올림하고, KO 확률은 화면에서 소수 둘째 자리까지 반올림한다. 엔진 설명문은 퍼센트 버림과 KO 확률의 다른 정밀도를 사용하므로 수치 표시를 설명문 파싱에 의존하지 않는다. 근사 표시와 원문은 별도 보존한다.
- **KO 한계 처리:** 설치본의 `kochance()`는 1~4타의 확률을 계산한다. 5~9타에서는 최소·최대 누적 데미지에 따라 확정 또는 가능 여부를 반환하며, 가능한 경우에도 정확한 확률을 반환하지 않을 수 있다. 9타를 넘어가면 빈 결과를 반환한다. 계산됨·확률 미산출·계산 범위 초과·데미지 무효를 별도 상태로 구분하며, 미산출 확률은 `null`로 유지한다. 9타 초과를 KO 불가나 0%로 표시하지 않는다.
- **대안과 감수한 점:** 웹에서 엔진을 직접 호출할 수 있지만 입력 검증과 결과 변환을 계산 패키지에 모아 UI 없이도 검증한다. 모든 엔진 입력과 도구를 즉시 공개하는 대신 검증한 범위의 계약부터 제공한다. 전체 입력 계약, 세팅의 게임 내 적법성, 추가 기술·특성·도구 지원은 별도 검증이 필요하다. 작은 검증 화면의 입력은 `useState`로 관리하며 전체 계산기의 `useReducer` 방향을 변경하지 않는다.
- **당시 테스트 도구:** Node.js 26의 TypeScript 실행과 내장 테스트 러너로 실제 계산 함수를 실행했다. 별도 테스트 프레임워크나 계산 패키지 빌드 없이 검증했다.

### 조건부 입력 데이터와 엔진 호환성 후속 조사

- **데이터 구성:** 엔진 계산 데이터는 유지하고 전체 특성 슬롯·습득 기술·폼 연결·추가 입력 분류를 파일로 보완한다. 기준은 Showdown 커밋 `f827a1d41064e0dec4c19c6ea0394fcf0c23479c`와 설치된 `@smogon/calc@0.12.0`이다. 원본·생성기·산출 파일과 설치 엔진·앱 코드의 해시로 조사 조건을 고정한다. 공개 데이터에 DB를 추가하지 않았다.
- **대조 범위:** 추가 입력 대상 기술 33개·특성 17개 전체의 164개 조건 사례에서 원본 콜백의 기대 조건/위력/성공 여부, 엔진 직접 호출, 앱 함수를 비교했다. 트리플악셀·찍찍베기는 실제 적중 횟수를 받을 수 있어 횟수 입력 분류에 포함했다. 조건부 입력 UI나 실제 계산 보완은 아직 구현하지 않았다.
- **책임 구분:** 20개는 검사한 조건에서 엔진 보정이 일치하며 앱의 입력·전달·결과 형식 보완이 필요하다. 6개는 일부 반영이다. 보복은 실제 행동 순서 대신 속도로 추정하고, 애널라이즈의 `abilityOn=false`는 강제 OFF가 아니다. 심록·맹화·급류·벌레의알림은 실제 저HP 발동은 맞지만 HP 100%에서 발동 토글을 강제할 수 없다.
- **엔진 공백:** 성묘·분노의주먹·토해내기·집단구타·반사 데미지 기술 및 일부 행동 이력 위력 기술 등 15개는 해당 조건 계산이 없다. 원본 규칙으로 위력을 정한 뒤 엔진에 넘기는 경우, 고정 데미지를 별도로 만드는 경우, 아군별 타격을 계산하는 경우를 구분해야 한다. 보복처럼 내부 분기가 다시 보정하는 기술은 단순 위력 override만으로 해결되지 않는다.
- **호출 전 판정:** 기습·속이다 등 기술 성공 여부와 트레이스의 복사 결과 등 8개는 앱에서 문맥을 판정해야 한다. 이를 모두 엔진 버그로 기록하지 않는다. 리시버는 아군 기절이 필요해 현재 싱글에는 발동 맥락이 없으며 별도 전투 가정을 도입하지 않았다.
- **상태 전이 후속 검증(2026-11-18):** 이전 보류 80개를 296개 조건으로 대조했다. 엔진 반영 10개, 일부 반영 49개, 해당 조건 미반영 9개, 사건·기술 위임의 호출 전 처리 필요 9개, 싱글 맥락 없음 1개, 직접 데미지 계약 밖 2개다. 이번 범위의 검증 미완료 항목은 0개다. 무게 기술은 구간 경계와 현재 게임에서 불필요한 다이맥스 분기를 구분했다. 멀티스케일은 반복 데미지와 단발 결과 KO 질의가 다르며 옹골참 생존도 KO에 반영되지 않았다. 도구·타입·랭크·폼 변화는 첫 데미지, 기술 후 상태, 다음 공격을 구분했다.

## D16. PokéAPI 공식 일러스트와 비상업적 운영·권리 고지

- **문제와 범위:** 계산 화면에서 포켓몬을 식별할 수 있는 이미지의 제공처와 스타일을 조사하고, 서비스의 운영 목적·권리 고지 방향을 정한다. 이미지 연결과 고지 UI는 아직 구현 범위에 포함하지 않는다.
- **선택과 대안:** PokéAPI Sprites의 `other/official-artwork` 정적 PNG로 이미지 스타일을 통일한다. HOME 이미지, 도트 이미지와 애니메이션도 제공되지만 공식 일러스트를 사용하는 방향으로 정했다. 이미지 없는 화면은 외부 이미지 의존성을 없애는 대안이다.
- **선택 이유:** 포켓몬을 식별할 수 있는 정적 일러스트로 화면의 이미지 스타일을 통일한다. 현재 계산 화면에는 애니메이션 재생이 필요하지 않다.
- **조사 결과와 후속 확인:** PokéAPI 데이터에서 한카리아스 ID `445`, 메가 메타그로스 ID `10076`을 확인했다. 메가진화를 기본 종의 도감 번호에만 연결하지 않아야 한다. 전체 포켓몬·폼 매핑과 이미지 전달 방식은 구현 단계에서 정하고 검증한다.
- **운영과 고지 방향:** 학습 및 정보 제공을 위한 비상업적 팬 프로젝트로 운영한다. 비상업적 목적, 포켓몬 이미지·명칭의 권리자, 관련 회사의 공식 승인·후원·제휴 관계 부재, PokéAPI 출처와 이미지 라이선스 링크를 표시할 예정이다. 고지의 위치와 컴포넌트 구성은 구현 단계에서 정한다.
- **권리 확인의 한계:** PokéAPI 저장소는 CC0를 표시하면서 이미지 저작권이 The Pokémon Company에 있다고 명시하고, 제3자의 권리 해결이나 필요한 허락의 확보를 보장하지 않는다. 이미지에 대한 개별 사용 허락은 확인되지 않았다. 다른 사이트의 사용 사례, 비상업적 목적과 권리자 고지를 권리자의 묵시적 허락 또는 적법성 확인으로 취급하지 않는다. 이 상태에서 이미지를 사용하는 제약을 유지하며 운영 범위 변경 시 사용 조건을 다시 검토한다.
- **현재 상태:** 이미지 제공처·형식과 대표 포켓몬·폼의 식별자를 조사하고 사용 방향을 정했다. 저장소의 이미지 연결·고지 UI·외부 이미지 설정은 미적용 상태다. 전체 지원 포켓몬의 이미지 존재 여부나 법적 사용 권한을 검증한 것은 아니다.
- **확인 자료:** [PokéAPI 이미지와 형식](https://github.com/PokeAPI/sprites#sprites), [PokéAPI 포켓몬·폼 ID 데이터](https://github.com/PokeAPI/pokeapi/blob/master/data/v2/csv/pokemon.csv), [이미지 저장소 라이선스](https://github.com/PokeAPI/sprites/blob/master/LICENCE.txt), [Pokémon 공식 이미지 사용 안내](https://support.pokemon.com/hc/en-us/articles/360000634094-Can-I-use-Pok%C3%A9mon-images-or-materials), [CC0와 제3자 권리](https://wiki.creativecommons.org/wiki/CC0_FAQ).

## D17. 로컬 PostgreSQL과 서비스·마이그레이션 역할 분리

- **문제와 범위:** 앱 연결 전에 로컬 DB의 실행·인증·권한을 독립적으로 확인하고, 실행 중인 앱의 자격증명으로 테이블 구조나 마이그레이션 이력을 변경하지 못하게 한다. [#8](https://github.com/nickwildee/champsparty/issues/8)의 로컬 구성 범위이며 배포용 DB 서비스는 선택하지 않았다.
- **실행 방식과 대안:** Homebrew PostgreSQL `18.7`을 설치하고 `brew services run postgresql@18`로 필요할 때 실행한다. Docker는 별도 런타임·컨테이너 관리가 추가되므로 현재 도입하지 않고, 환경 재현 등 필요가 생기면 검토한다. 로그인 시 자동 실행 대신 수동 시작·중지를 사용한다.
- **역할 분리와 대안:** `champsparty` DB의 소유자는 `champsparty_migrator`이고, 앱은 `champsparty_app`으로 접속한다. 단일 역할은 접속 정보 관리가 단순하지만 앱도 구조 변경 권한을 갖게 된다. 두 역할로 분리해 앱의 허용 범위를 데이터 처리로 제한하는 대신 비밀번호 두 개와 실행 목적별 환경 파일을 관리한다. 두 역할 모두 슈퍼유저·DB 생성·역할 생성·복제·RLS 우회 권한을 부여하지 않는다.
- **스키마·자동 권한:** migrator가 `public`과 `drizzle`을 소유한다. `public`은 서비스 테이블, `drizzle`은 마이그레이션 이력에 사용한다. DB와 두 스키마의 기본 `PUBLIC` 권한을 회수하고 앱에는 DB의 `CONNECT`와 `public`의 `USAGE`만 부여한다. `ALTER DEFAULT PRIVILEGES FOR ROLE champsparty_migrator IN SCHEMA public`로 새 테이블의 `SELECT`·`INSERT`·`UPDATE`·`DELETE`를 앱에 자동 부여한다. 이 규칙은 migrator가 생성하는 테이블에 적용되므로 마이그레이션 실행 역할을 유지해야 한다. 앱의 `CREATE`·`TEMP`·`TRUNCATE`·구조 변경·객체 삭제·이력 스키마 접근과 migrator 역할 전환은 허용하지 않는다.
- **비밀값 보관:** 역할마다 별도로 생성한 64자 무작위 16진수 비밀번호를 사용한다. `apps/web/.env.local`의 `DATABASE_URL`은 앱 역할, `apps/web/.env.migrations.local`의 `MIGRATION_DATABASE_URL`은 migrator 역할이다. 두 파일은 Git 제외와 권한 `0600`을 확인했다. 마이그레이션 전용 파일은 Next.js의 자동 로딩 대상이 아니며 후속 도구 설정에서 명시적으로 로드해야 한다. URL·비밀번호·해시를 문서나 이슈에 남기지 않는다.
- **로컬 인증과 관리 접속:** 두 프로젝트 역할의 IPv4 `127.0.0.1/32`·IPv6 `::1/128`·Unix 소켓에 `scram-sha-256` 규칙을 먼저 적용했다. DB 이름과 무관하게 적용해 다른 DB로 접속하며 후순위 `trust` 규칙을 선택하지 못하게 한다. 기존 `heoknoh` 관리 역할은 Homebrew 초기화 시 만들어진 로컬 슈퍼유저이며 비밀번호가 설정되지 않았다. 기존 관리 접속의 `trust` 규칙은 보존했다. 따라서 관리 역할의 비밀번호 인증까지 적용한 구성이 아니며, 이 설정을 배포 환경의 인증 정책으로 사용하지 않는다. 변경 전 HBA 파일은 같은 디렉터리의 `pg_hba.conf.champsparty-before-scram`에 보관했다.
- **실행 검증:** PostgreSQL `18.7`·UTF8 DB·소유자·역할 속성·스키마 권한을 확인했다. 두 역할 × 세 경로 × 정상·오류·누락 비밀번호의 18개 인증 경우, 다른 DB 이름의 오류 비밀번호 거부 2개를 포함해 총 40개 항목이 통과했다. migrator가 만든 테스트 테이블에서 앱의 자동 데이터 권한과 구조·이력 접근 거부 9개, migrator의 구조 변경을 확인하고 테스트 객체를 제거했다. 서버 중지·수동 재실행 후 두 역할의 재접속과 오류 비밀번호 거부를 다시 확인했다. 최종 상태는 실행 중·자동 실행 미등록, HBA 구문 오류 0개, 서비스·이력 테이블 0개다.
- **남은 범위:** pg·Drizzle 설치와 서버 연결, 이력 저장 스키마 설정·실제 마이그레이션, Better Auth 인증 테이블과 네이버 로그인·세션 검증은 후속 이슈에서 다룬다. 이번 DB 직접 검증을 앱의 연결·인증 완료로 해석하지 않는다.
- **확인 자료:** [PostgreSQL 비밀번호 인증](https://www.postgresql.org/docs/18/auth-password.html), [HBA 규칙과 적용 순서](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html), [기본 권한 설정](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html), [권한의 종류](https://www.postgresql.org/docs/18/ddl-priv.html).

## D18. 앱 DB 연결과 검증 방식

- **문제와 범위:** [#9](https://github.com/nickwildee/champsparty/issues/9)에서 `apps/web`의 서버 코드가 Drizzle과 pg를 통해 로컬 PostgreSQL에 접근하는 공통 연결을 설계한다. 앱 접속에는 D17의 `champsparty_app`과 `DATABASE_URL`을 사용한다. 연결 모듈·환경변수 검사·터미널 명령을 구현하고 실제 DB·Next.js 서버에서 검증했다. 인증 스키마와 로그인 구현은 포함하지 않는다.
- **연결 관리와 대안:** 실행 중인 서버의 같은 JavaScript 실행 환경에서 pg의 풀 하나를 재사용한다. DB 작업마다 새 연결을 만들고 종료하는 방법은 재사용할 작업이 적을 때 단순하지만, 웹앱의 반복 요청에서는 접속 준비 비용이 반복된다. 풀을 재사용하는 대신 연결 한도·반납·유휴 정리와 오류 처리를 관리해야 한다. 서로 다른 서버 실행 환경의 풀은 각각 별도이며 연결을 직접 공유하지 않는다.
- **로컬 개발용 시작값:** 풀당 `max: 10`, `connectionTimeoutMillis: 5000`, `idleTimeoutMillis: 10000`을 사용한다. 연결은 필요할 때 생성하며 최대 10개를 허용한다. 연결 획득 대기·새 연결 생성에는 5초 제한을 두고, 반납된 연결은 10초 동안 사용하지 않으면 정리한다. 연결 획득 시간 제한은 SQL 실행 시간 제한과 구분한다. 최대 연결 수와 유휴 정리 시간은 pg의 기본값을 유지하며, 5초는 로컬 개발 중 연결 문제를 오래 기다리지 않도록 정한 시작값이다. 성능 측정으로 찾은 최적값은 아니며, 실제 대기가 문제가 되면 원인과 설정을 검토한다. 서버 실행 환경이 늘어나는 배포에서는 전체 연결 수를 다시 검토한다.
- **개발 중 풀 재사용:** 개발 모드에서는 `globalThis`에 만든 풀을 보관하고, 코드가 다시 실행될 때 기존 풀이 있으면 재사용한다. 일반 모듈 변수에만 보관하는 방법보다 보관·재사용 코드가 추가되지만, 개발 중 모듈 재실행으로 풀이 중복 생성되는 것을 방지하는 방향이다. DB 접속 정보나 풀 설정 변경 시 개발 서버를 완전히 재시작한다. 이 보관은 같은 JavaScript 실행 환경의 메모리에 한정되며 서버 재시작 후에는 새 풀을 만든다.
- **서버 전용 경계:** DB 연결 파일에 `import "server-only"`를 넣어 Client Component에서 잘못 가져다 쓰면 Next.js 빌드 과정에서 오류가 나도록 한다. 서버용 폴더·사용 규칙만으로 구분하는 대안보다 자동 검사로 잘못된 사용을 발견한다. 브라우저에서 실행하는 계산 코드는 이 연결 모듈을 사용하지 않는다.
- **환경변수 검사 시점:** DB 연결 파일을 불러오는 즉시 검사하는 대신, DB 기능을 처음 사용할 때 `DATABASE_URL` 누락을 검사한다. DB와 무관한 계산 코드가 접속 설정을 불필요하게 요구하지 않도록 하고, DB 기능 호출 시에는 설정 이름을 포함한 명확한 오류를 낸다. 실제 접속 URL·비밀번호는 오류나 로그에 넣지 않는다. DB 기능을 사용하기 전까지 누락을 발견하지 못할 수 있으므로 접속 확인 명령에서도 누락을 검증한다. 값의 존재와 실제 DB 접속 성공은 별도로 확인한다.
- **터미널 환경 파일 로딩:** 접속 확인 명령은 `@next/env`로 `apps/web`의 환경 파일을 Next.js 개발 환경과 같은 규칙으로 읽은 뒤 공통 DB 연결 코드를 호출한다. Node.js 내장 환경 파일 옵션으로 파일을 직접 지정하는 대안도 가능하지만, 앱과 확인 명령의 파일 선택·우선순위를 일치시키는 방향을 선택했다. `@next/env`를 직접 사용하는 의존성으로 명시해 관리한다. 앱용 `DATABASE_URL`을 사용하며 마이그레이션 전용 환경 파일의 로딩은 후속 작업이다.
- **접속 확인 경로:** 확인용 공개 API를 추가하는 대신 터미널 명령으로 검증한다. 앱과 같은 DB 연결 코드에서 `SELECT 1`, 접속 DB 이름과 역할을 확인하며 기대 대상은 `champsparty`·`champsparty_app`이다. 확인을 위해 테이블이나 데이터를 생성·변경하지 않는다. Next.js 외부의 실행 환경에서 환경 파일 로딩과 서버 전용 코드 실행 구성을 마련해야 한다는 점을 감수한다. 프로젝트 루트의 `pnpm db:check`로 실행한다. 성공·실패를 종료 코드 0·1로 구분하고 항상 이 명령 프로세스의 풀을 정리한다. 실행 중인 Next.js 서버의 풀에는 영향을 주지 않는다.
- **DB 오류 처리:** 쿼리·연결 오류는 호출한 서버 코드에 전달하며 공통 연결 코드에서 Next.js 프로세스를 강제 종료하지 않는다. 유휴 연결의 오류 이벤트에는 처리기를 등록해 비밀값 없는 오류 정보를 남긴다. 실패를 성공한 결과로 숨기지 않으며, 화면·API의 오류 응답은 각 기능에서 처리한다. 잘못된 비밀번호·설정 누락으로 DB 요청이 실패한 뒤 일반 Next.js 페이지가 정상 응답하는 것을 확인했다. 그 외의 장애 종류는 같은 결과를 검증한 것으로 확대하지 않는다.
- **자동 재시도:** 공통 연결 코드에서는 실패한 작업을 자동 재시도하지 않는다. 쓰기 요청의 결과가 불명확할 때 같은 작업을 반복할 위험을 피하고 재시도 여부를 업무 로직에서 판단하도록 한다. 이후 별도 요청의 새 연결 시도와 실패한 SQL의 자동 재실행은 구분한다.
- **버전과 배치:** `apps/web`의 런타임 의존성은 `pg 8.23.1`, `drizzle-orm 0.45.4`, `server-only 0.0.1`이며 개발 의존성은 `@types/pg 8.23.1`, `@next/env 16.4.6`, `tsx 4.23.15`다. 모두 정확한 버전으로 고정했다. `@next/env`는 Next.js 버전에 맞췄다. 공통 연결은 `apps/web/src/server/db.ts`의 `getDb()`·`closeDb()`, 확인 명령은 `apps/web/scripts/db-check.ts`에 둔다. 현재 소비자인 웹 앱 안에 두며 공용 DB 패키지는 추가하지 않았다. 값 없는 `apps/web/.env.example`에 `DATABASE_URL` 이름을 안내한다.
- **명령 실행과 대안:** 앱 명령은 `NODE_ENV=development node --conditions=react-server --import=tsx scripts/db-check.ts`다. 개발 모드를 명령 프로세스에 지정하고 `@next/env`의 개발 환경 로딩을 사용한다. pnpm이 앱 폴더에서 실행하므로 그 위치의 환경 파일을 읽는다. Node.js 내장 TypeScript 실행 대신 `tsx`를 사용해 앱의 TypeScript 모듈을 실행하며 개발 의존성 증가를 감수한다. 타입 검사는 별도로 한다. `react-server` 조건은 해당 명령에만 적용하며 Next.js의 클라이언트 경계 검사를 변경하지 않는다. 현재 실행 명령은 macOS의 POSIX 셸 기준이며 Windows 실행 방식은 검증하지 않았다.
- **설치 오류와 해결:** pnpm 12의 기본 설치 정책이 `tsx`의 의존성 `esbuild 0.28.2`의 설치 후 스크립트를 미판정 상태로 차단했다. 스크립트 생략 시 접속 명령은 동작했지만 일반 재설치는 실패했다. 플랫폼 실행 파일 준비·버전 검사를 담당하는 스크립트를 확인하고 `pnpm-workspace.yaml`의 `allowBuilds`에서 `esbuild@0.28.2`만 허용했다. 모든 패키지 또는 향후 버전 전체 허용은 선택하지 않았다. `pnpm rebuild esbuild`와 이후 일반 `pnpm install --frozen-lockfile`이 통과했다. 버전 변경 시 해당 허용 범위를 다시 검토한다.
- **실행 검증:** Node.js `26.13.1`·pnpm `12.19.0`·PostgreSQL `18.7`에서 루트 `pnpm db:check`가 읽기 쿼리로 `champsparty`·`champsparty_app`을 확인하고 종료 코드 0으로 끝났다. 임시 검증의 7개 시나리오에서 정상 접속, 환경변수 누락, 잘못된 비밀번호, 서버 접속 실패, 다른 역할의 접속 거부, 서버 전용 조건 없는 직접 import 거부, 연결 수명주기를 확인했다. 수명주기 검증에는 import 시 설정 미검사·첫 호출 시 검사, 최초 연결 0개, 풀 설정, 모듈 재로딩 후 같은 풀·단일 오류 처리기 재사용, 유휴 오류의 비밀값 없는 처리, SQL 오류 전달·자동 재실행 없음·후속 쿼리 성공과 풀 종료를 포함했다. 오류 출력에 접속 URL·비밀번호가 없는 것을 확인했다.
- **Next.js 검증:** DB 모듈을 가져오는 임시 Client Component의 프로덕션 빌드가 `server-only` 오류로 거부됐다. 임시 Server Component를 포함한 빌드는 `DATABASE_URL` 없이 통과했다. 실제 로컬 Next.js 프로덕션 서버에서 DB 읽기 성공 응답 200, 잘못된 비밀번호·누락 설정의 DB 요청 500과 각 오류 이후 일반 페이지 200을 확인했다. 사용한 임시 페이지·서버는 제거했다. 배포할 확인용 API·페이지나 DB 테이블·데이터는 생성하지 않았다.
- **검증 경계와 후속 범위:** 타입 검사·린트·peer 검사·일반 frozen-lockfile 설치와 임시 페이지 제거 후 최종 프로덕션 빌드를 통과했다. 서식·문서 링크·공백 검사도 통과했다. 모듈 재로딩 검증은 같은 Node 실행 환경의 캐시 재로딩이며 실제 Next.js 편집 이벤트 전체를 검증한 것은 아니다. 배포용 연결 수·사전 점검과 장애 종류별 복구는 후속 검토 대상이다. 인증 스키마·마이그레이션·네이버 로그인·세션은 이번 검증에 포함하지 않는다.

## 앞으로 결정 기록을 갱신할 때

- 요구사항과 기술적 결정의 변경은 기존 배경과 변경 이유를 남긴다. 기록 기준에 맞지 않는 학습 대화·일반 개념 설명은 제외한다.
- 동작·설계·제약에 영향을 준 의견과 선택 이유를 간결하게 기록하고, 설명·동의·승인 과정과 이해도는 기록하지 않는다.
- 측정 결과는 실제 환경과 조건을 함께 남긴다. 예정된 개선과 달성한 개선을 분리한다.
- 새로운 기록 형식이나 파일을 늘리기 전에 현재 문서 안에서 필요한 기록을 관리할 수 있는지 판단한다.
