## D01. 숙련자의 세팅 조정을 위한 현재 결과 표시

- **배경:** 사용자는 이미 실전 포켓몬을 다룰 수 있다. 직접 정한 여러 상대에 대한 가능성을 한눈에 보고 싶어 한다.
- **합의:** 현재 입력의 스피드, 데미지 범위, KO 타수·확률, 결정력·내구를 제공한다.
- **사용자 수정:** 변경 전후를 비교할 필요가 있는지에 대해, 현재 능력치에서 어떤 결과가 나오는지만 보여 주는 것이 목적이라고 명확히 했다.
- **검토했던 대안:** 변경 전후 비교, 변화 알림, 파티 취약점 분석과 추천.
- **선택 이유:** 사용자가 판단할 수 있는 계산 정보를 제공하고 입력·확인 동선을 단순하게 유지한다.
- **범위:** 비교 이력, 자동 추천과 취약점 보고서를 현재 MVP에 포함하지 않는다.

## D02. 챔피언스만 지원하고 기존 계산 엔진 활용

- **배경:** 사용자는 직접 구현의 주된 부담을 많은 데이터의 재입력으로 보았다. 지원 게임을 챔피언스로 제한하면 직접 구현도 가능하지 않은지 검토했다.
- **합의:** `@smogon/calc`를 활용한다. 직접 계산 엔진 전체를 새로 만드는 방향은 채택하지 않는다.
- **사용자 선택:** 참고 서비스가 같은 계열의 엔진을 사용한다는 논의 이후, 기존 엔진을 가져다 쓰는 방향으로 변경했다.
- **대안:** 챔피언스 전용 엔진 직접 구현, 여러 게임을 지원하는 범용 계산기 구성.
- **선택 이유:** 기존 계산 로직과 데이터를 활용하고, 이 프로젝트의 핵심인 다수 상대 입력·즉시 갱신·저장 경험에 집중한다.
- **검증 필요:** 실제 설치할 배포 버전의 챔피언스 지원, 데이터 범위, 능력치 입력 변환과 난수 결과. 저장소 소스에서 지원 코드가 보인다는 사실만으로 설치 버전까지 검증한 것으로 쓰지 않는다.

## D03. 회복 효과는 제외하고 도구별 지원을 구분

- **초기 아이디어:** 자뭉열매와 먹다남은음식 같은 회복을 고려한 KO 타수 계산.
- **변경된 합의:** 회복 효과를 포함한 전투 진행 계산은 MVP에서 제외한다. 포켓몬별로 시작 랭크와 현재 HP를 입력한다. HP를 빠르게 조절할 때는 슬라이더를 움직이고, 원하는 퍼센트가 정해져 있으면 표시된 숫자를 눌러 직접 입력한다. 두 조작은 같은 정수값(1~100%, 기본 100%)을 양방향으로 갱신한다. 각 포켓몬에서 해당 비율로 표시될 수 있는 가장 큰 HP를 채택한다. 예를 들어 최대 HP 175에서는 88과 89가 모두 50%로 표시되므로 89를 사용한다.
- **사용자 이유:** 파티 준비를 위한 계산기에 전투 내부의 변수를 지나치게 넣으면 제공할 정보와 범위가 커진다고 판단했다.
- **이후 논의:** 엔진의 회복 및 반감열매 지원 여부와, 부족한 처리의 추가 구현 가능성을 확인했다.
- **현재 기준:** 가능성 조사가 회복 기능의 재도입 승인을 뜻하지 않는다. 반감열매의 첫 타 감소와 반복 공격 중 소비는 별도로 검증한다.
- **확률의 의미:** 동일 기술을 N회 사용해 모두 명중했을 때 N회 이내에 쓰러뜨릴 확률로 해석한다. 앞서 합의한 이 의미는 유지하며, 이후 철회된 회복 반영은 제외한다.
- **검증 필요:** 정확한 KO 확률이 성립하는 입력 범위와 엔진의 정밀도. 추가 보완이 필요하면 범위와 방법을 먼저 논의한다.

## D04. 공통 내 세팅과 통합 상대 목록, 상대별 비교 목적

- **초기 방향:** 내 포켓몬 세팅은 공유하되 스피드·공격·방어별 상대 목록을 따로 두고, 각 목록에 상대를 0~5마리까지 추가하며 계산 영역을 전환해 결과를 확인하도록 했다.
- **변경 배경(2026-11-17):** 능력치를 배분할 때 특정 공격을 버틸 수 있는지, 필요한 상대보다 빠른지, 공격 포인트를 줄여도 KO 타수·확률이 유지되는지를 함께 판단해야 한다. 영역별로 분리된 목록과 화면 전환은 서로 다른 목적의 결과를 오가며 확인하게 하고, 같은 상대 세팅의 중복 입력을 요구할 수 있다.
- **현재 합의:** 하나의 내 포켓몬 세팅과 통합 상대 목록을 사용한다. 상대마다 공격·방어·스피드 비교 목적을 하나 이상 선택하고, 여러 목적을 함께 지정할 수 있다. 한 상대의 여러 비교는 같은 상대 세팅을 공유하며, 내 입력을 수정하면 선택한 모든 비교 결과를 한 화면에서 갱신한다.
- **대안:** 영역별 목록을 유지하고 결과만 한 화면에 모으는 최소안은 기존 구성을 적게 바꿀 수 있지만, 같은 상대 세팅을 목적별로 반복 입력할 수 있다. 상대 목록과 비교 목적을 함께 통합하는 방향을 선택했다.
- **선택 이유:** 사용자가 직접 능력치를 조정하면서 공격 성능·생존 가능성·스피드를 함께 확인하도록 하고, 같은 상대에 대한 반복 입력과 결과 확인을 위한 화면 전환을 줄이는 구조다. 동선과 사용성 개선의 실제 효과는 구현 후 검증한다.
- **입력과 표시:** 상대는 필요한 만큼 한 마리씩 추가·수정·제거한다. 상대별로 선택한 목적에 필요한 입력과 결과를 제공하고, 상세 입력을 접어 결과 요약을 우선 확인할 수 있게 한다. KO 결과는 타수와 확률을 함께 표시한다.
- **저장·복원:** 브라우저의 작업 복원 대상에 통합 상대 목록과 상대별 비교 목적·계산 조건을 포함한다. 계정에 저장한 내 세팅을 불러올 때 이 상대 목록과 목적·조건을 유지한다. 상대 목록의 명시적 계정 저장은 추가하지 않는다.
- **감수할 점:** 상대별 다중 목적에 따른 입력 폼과 결과 배치를 설계해야 한다. PC와 모바일에서 정보량·스크롤과 입력 응답성을 확인해야 한다.
- **미정·범위:** 기존 영역별 5마리 제한을 통합 목록의 상한으로 그대로 적용하지 않으며, 통합 목록의 최대 상대 수는 별도로 확정한다. 자동 능력치 배분 추천, 변경 전후 비교와 자동 이력은 MVP에 추가하지 않는다.
- **화면 방향:** PC에서 왼쪽에는 내 포켓몬 기본 입력, 오른쪽에는 상대별 공격·방어·스피드 결과를 둔다. 상세 설정은 선택한 상대만 펼친다. 상대별 필드는 양쪽 벽을 분리한 뒤 같은 상대의 세 비교에서 공유한다.
- **검증 상태:** 기본 입력과 펼침 상태를 PC 시안에서 확인할 수 있다. 전체 UI와 계산 동작은 구현·검증 전이다. 상대·비교 목적의 추가·수정·제거, 한 상대의 여러 목적 간 세팅 공유, 내 입력 변경 시 모든 선택 결과의 갱신, 저장본 불러오기·로컬 복원과 PC·모바일 주요 흐름을 검증한다.

## D05. 기준 세팅 저장과 작업 화면 복원을 분리

- **배경:** 사용자는 내 포켓몬 세팅을 저장하고 나중에 불러와 조정하고 싶어 한다. 마지막 입력을 복원하는 편의도 함께 검토했다.
- **합의:** 내 포켓몬 세팅은 명시적으로 계정에 저장한다. 편집 중인 내 세팅, 통합 상대 목록과 상대별 비교 목적·계산 조건을 포함한 작업 화면은 브라우저 로컬에서 자동 복원한다.
- **대안:** 모든 입력을 계정에 자동 저장하거나 전체 작업 화면을 명시적 저장 단위로 삼는 방식.
- **선택 이유:** 저장한 기준 세팅과 실험 중인 입력을 구분하면서 반복 입력 부담을 줄인다. 계정 저장본은 기기를 바꾸어 불러올 수 있다.
- **불러오기 규칙:** 사용자가 선택한 저장 세팅으로 내 입력을 교체하되 통합 상대 목록과 상대별 비교 목적·계산 조건은 유지한다. 이전 입력을 모두 별도 이력으로 보관하지 않는다.
- **범위:** 작업 초안의 기기 간 자동 동기화와 전체 파티·상대 목록의 계정 저장은 추가하지 않는다.

## D06. 편집 중인 입력을 서버 갱신으로 덮어쓰지 않음

- **논의의 핵심:** 저장한 한카리아스 세팅을 불러와 수정하는 중에 저장 목록이 다시 조회되더라도, 현재 편집값이 원래 저장값으로 돌아가면 안 된다.
- **합의:** 저장 데이터를 조회하는 상태와 계산기에 적용한 작업 입력을 분리한다. 명시적 불러오기에서만 저장 데이터를 작업 입력에 적용한다.
- **갱신 방향:** 목록을 열거나 저장·수정·삭제 결과를 반영하는 등 필요한 시점에 서버 데이터를 갱신한다. 노력치 입력 변경을 서버 재조회와 연결하지 않는다.
- **복원 규칙:** 이전 로컬 작업을 확인·복원한 뒤 자동 저장을 시작한다.
- **검증할 흐름:** 불러오기 후 수정 → 서버 목록 갱신 → 입력 유지, 새로 열기 → 기존 초안 복원 → 이후 변경 저장.
- **미정:** Query의 구체적인 캐시 시간과 재조회 옵션, 로컬 저장 형식과 갱신 방식.

## D07. 작은 풀스택 모노레포로 시작

- **합의:** Next.js + TypeScript를 사용하고, 웹과 서버 기능을 한 Next.js 애플리케이션에서 제공한다. 계산 로직은 별도 패키지로 분리한다.
- **패키지 경계.** 웹은 `apps/web`, 계산 로직은 `packages/calculator`에 두고 pnpm 워크스페이스로 연결한다. 실제 연결 방식은 [D14 패키지 연결](#d14-두-패키지-연결과-최소-nextjs-실행-환경)에 기록했다.
- **대안:** 처음부터 독립 API 서버를 두거나 여러 공유 패키지와 추가 모노레포 도구를 함께 도입하는 방식.
- **선택 이유:** 현재 서버의 핵심 역할은 인증과 개인 세팅 저장이다. 지금 필요한 경계부터 두고 운영·개발 구성을 작게 유지한다.
- **사용자 기준:** 실제 필요가 생겼을 때 사용하고, 이후 필요한 경우 마이그레이션한다는 방향에 동의했다.
- **재검토 조건:** 서버의 독립 배포 등 구체적인 요구가 생겼을 때 분리를 검토한다. 나중에 쓸 수도 있다는 이유만으로 구조를 미리 늘리지 않는다.

## D08. 계산은 브라우저, 계산 패키지는 입력과 출력에 집중

- **구현 방향:** 현재 입력을 계산 엔진이 받을 형태로 변환하고, 결과를 화면에서 사용할 형태로 정리하는 계산 로직을 `packages/calculator`에 둔다. 계산은 브라우저에서 수행한다.
- **대안:** 입력을 바꿀 때마다 서버에 계산 요청을 보내는 방식.
- **선택 이유:** 실시간 조정에 필요한 계산을 네트워크 왕복과 분리하고, 계산 로직을 화면 코드와 별도로 검증한다.
- **경계:** 계산 패키지는 UI, 인증, DB 연결과 로컬 저장을 직접 관리하지 않는다.
- **감수할 점:** 브라우저로 전달되는 데이터·코드 크기와 모바일의 계산 응답성을 실제로 확인해야 한다.
- **검증과 개선:** 입력 반응, 계산 시간과 초기 로딩을 측정한 뒤 필요하면 최적화한다. Worker나 추가 캐시를 처음부터 필수로 정하지 않는다.

## D09. 작업 상태와 서버 상태를 목적에 맞게 관리

- **구현 방향:** 계산기 작업 입력은 React `useReducer`, 작은 UI 상태는 필요에 따라 `useState`, 저장된 서버 세팅은 TanStack Query로 관리한다.
- **계산 결과:** 현재 입력으로부터 파생한다. 입력과 별도로 수정 가능한 중복 결과 상태를 기본 구조로 두지 않는다.
- **대안:** 모든 입력을 개별 `useState`로 관리하거나 Zustand 같은 외부 상태 관리 도구를 사용하는 방식.
- **선택 이유:** 내 세팅 수정, 상대 추가·수정·삭제, 저장본 적용 등의 변경을 액션으로 모으고, 서버 데이터의 조회·갱신 상태는 별도로 다룬다.
- **주의할 해석:** `useReducer`를 선택했다고 렌더링 성능이 자동으로 개선되는 것은 아니다. 상태 공유나 구독 요구가 달라지면 다른 도구도 검토할 수 있다.
- **검증 필요:** 상태 변경 흐름, 계산 갱신, 복원 순서와 서버 갱신 중 입력 유지.

## D10. 계정 저장에 PostgreSQL·Drizzle, 로그인은 네이버

- **선택.** PostgreSQL과 Drizzle을 사용하고, 네이버 로그인은 Better Auth로 연동하기로 했다.
- **대안:** 다른 ORM, 초기 후보였던 카카오 로그인, 인증 흐름을 직접 구성하는 방식.
- **선택 이유:** 사용자와 저장 세팅의 관계를 DB에 두고, TypeScript에서 스키마와 쿼리를 다루는 구성을 사용한다. 인증의 반복 작업은 라이브러리를 활용하는 방향이다.
- **범위:** 게임의 모든 계산 데이터를 DB에 다시 입력하는 것이 목적은 아니다. 계정에 저장할 사용자 세팅이 중심이다.
- 로컬 PostgreSQL과 역할 검증은 D17, 앱의 pg·Drizzle 연결은 D18, 인증 데이터와 저장 세팅의 관계는 D19, 인증 스키마와 네이버 제공자 구현·검증은 D20·D21에 기록했다.
- 실제 네이버 로그인과 브라우저 세션, 사용자별 저장 데이터 접근 제어는 후속 검증 대상이다. 배포용 DB 서비스는 미정이다. n3r 도입은 선택하지 않았다.

## D11. 생산성 중심 MVP 이후 실제 측정으로 개선

- **합의:** 핵심 기능이 정상적으로 동작하는 MVP를 먼저 만든 뒤 테스트와 성능 측정에서 발견한 문제를 개선한다.
- **사용자 의도:** 생산성을 위해 선택한 방법과 이후 정량적 개선을 이력서·면접에서 설명하고 싶어 한다. 일부러 품질을 떨어뜨려 개선 사례를 만들지는 않는다.
- **대안:** 처음부터 모든 예외와 최적화를 완성하거나, 수치 없이 개선을 주장하는 방식.
- **기록할 근거:** 당시 선택과 이유, 테스트 또는 측정 조건, 변경 전후 결과, 실제 사용자 흐름에서의 의미.
- **검증 방향:** 대표 계산 사례, 최대 상대 수에서의 입력·갱신, 저장·불러오기·복원, PC·모바일 주요 흐름을 확인한다.
- **미정:** 테스트 도구, 구체적인 성능 지표와 목표 수치. 같은 엔진을 쓰는 참고 서비스와 결과가 같다는 이유만으로 게임 규칙 전체의 독립 검증이 끝났다고 쓰지 않는다.

## D14. 두 패키지 연결과 최소 Next.js 실행 환경

[PR #5](https://github.com/nickwildee/champsparty/pull/5)에서 웹과 계산 패키지를 연결하고 개발·검사·빌드 명령을 마련했다. 당시 연결 검증에는 작은 버튼과 임시 함수를 사용했다.

- **등록과 의존성:** 루트의 `apps/*`·`packages/*` 등록을 유지하고 `@champsparty/web`, `@champsparty/calculator`를 구성했다. 웹의 `dependencies`에 계산 패키지를 `workspace:*`로 선언한다. 필요한 도구는 실행하는 패키지에 선언하며, 전체 저장소 서식을 다루는 Prettier는 루트에 둔다.
- **계산 패키지 공개 방식:** `exports`로 `src/index.ts`의 TypeScript 원본을 공개한다. Next.js가 워크스페이스 소스를 변환하므로 별도 계산 패키지 빌드·변경 감시나 `transpilePackages` 설정을 추가하지 않았다. 대안인 JavaScript·타입 선언 파일 사전 빌드는 독립 배포와 여러 소비 환경에 유리하지만, 당시 소비자는 웹 하나여서 원본 공개가 단순했다. 소비자가 TypeScript 변환 기능을 제공해야 한다는 제약을 감수한다.
- **계산 경계:** 계산 패키지는 React·Next.js·DOM·Node.js 전역 타입을 요구하지 않도록 자체 TypeScript 설정을 둔다. 당시에는 브라우저의 버튼 이벤트에서 임시 `add` 함수를 호출해 실제 동작을 확인했다.
- **Next.js 옵션:** Next.js `16.4.6`, React·React DOM `19.3.0`, App Router, TypeScript, `src/`, 웹 내부 별칭 `@/*`, 기본 Turbopack을 사용한다. 생성 도구의 옵션을 명시하고 설치를 건너뛴 뒤 두 패키지를 준비해 루트에서 설치했다. React Compiler와 Cache Components는 현재 요구에 필요하지 않아 활성화하지 않았다. 생성 도구가 만든 웹 내부 워크스페이스·중복 README·별도 gitignore를 제거하고 루트에서 관리한다.
- **지침 파일 자동 생성:** `--no-agents-md`는 초기 생성만 제어하며 `next dev`는 별도로 지침 파일을 만들었다. 설치 버전에 포함된 공식 설명을 확인해 `agentRules: false`로 자동 생성을 끄고 기존 루트 AGENTS.md를 사용한다. 임의로 공통 협업 지침을 추가하지 않는다.
- **스타일링:** Tailwind `4.3.3`과 공식 PostCSS 연동을 사용한다.
- **서식과 린트:** 루트에 Prettier `3.10.1`과 `format`·`format:check`를 구성했다. 각 ESLint 설정에 `eslint-config-prettier`를 적용하고 린트와 서식 검사는 별도로 실행한다. Git hook·별도 공통 설정 패키지는 추가하지 않는다.
- **검사 도구의 호환성:** 타입 검사는 TypeScript `5.9.3`을 두 패키지에서 사용한다. 최신 TypeScript `7.0.2`와 달리 현재 typescript-eslint `8.73.0`의 지원 범위는 `<6.1.0`이므로 호환되는 5.9 계열을 선택했다. 생성 도구의 ESLint 9는 설치 중 지원 종료 경고가 나와, Next.js 16.4에서 공식 지원하는 ESLint `10.15.0`을 사용한다. `eslint-plugin-import@2.32.0`, `eslint-plugin-jsx-a11y@6.10.2`, `eslint-plugin-react@7.37.5`의 peer 선언에는 10이 빠져 있어 이 세 버전에만 pnpm `overrides`의 `:peer` 선택자로 `^9 || ^10`을 지정했다. 실제 린트를 통과했으며 각 플러그인의 선언이 갱신되면 해당 보정을 제거한다. 모든 플러그인 기능을 별도로 재현한 검증은 아니다.
- **설치 기록:** pnpm `12.19.0`이 선택한 typescript-eslint `8.73.0` 계열의 최근 배포 버전에 대해 자동 추가한 정확한 버전의 `minimumReleaseAgeExclude` 항목을 유지했다. 전체 패키지의 출시 대기 시간을 끄는 설정은 사용하지 않는다. 실제 의존성과 로컬 연결은 루트 lockfile에 기록하며 생성된 코드·검사 캐시는 추적하지 않는다.
- **당시 확인 범위.** 고정 lockfile 설치, 두 패키지의 타입 검사·린트, 웹 빌드를 통과했다. 개발·프로덕션 브라우저에서 패키지 함수 호출과 Tailwind 적용을 확인했다. 샌드박스가 Turbopack의 내부 포트를 차단한 경우에는 캐시를 비우고 포트가 허용된 환경에서 같은 빌드를 검증했다. [도구 호환성과 실행 기록](https://github.com/nickwildee/champsparty/blob/3acde3fcd2a30c32f164aac2d14918d59951ca89/docs/DECISIONS.md#d14-두-패키지-연결과-최소-nextjs-실행-환경)
- **확인 자료:** [워크스페이스 프로토콜](https://pnpm.io/workspaces), [Next.js 워크스페이스 코드 변환](https://nextjs.org/docs/app/api-reference/config/next-config-js/transpilePackages), [Next.js ESLint 10 지원과 peer 경고](https://nextjs.org/docs/app/api-reference/config/eslint), [pnpm peer 범위 보정](https://pnpm.io/settings/dependency-resolution), [Tailwind Next.js 연동](https://tailwindcss.com/docs/installation/framework-guides/nextjs), [Prettier와 린터 통합](https://prettier.io/docs/integrating-with-linters).

## D15. 챔피언스 데미지 엔진의 설치와 싱글 검증 계약

싱글 계산기의 동작을 설계할 때는 [조건부 기술의 제품 규칙](#조건부-기술의-제품-규칙)을 본다. 엔진을 보완한 이유는 [당시 호환성 조사](#조건부-입력-데이터와-엔진-호환성-후속-조사)와 [CLI의 필드·접지 판정](#싱글-cli의-필드와-접지-판정)부터 이어지는 기록에서 찾을 수 있다. 제품에서 사용할 수 있는 입력과 현재 구현 범위는 [프로젝트 현황](PROJECT.md#현재-상태와-다음-작업)에서 확인한다.

- 계산은 `@smogon/calc@0.12.0`의 챔피언스 모드(`Generations.get(0)`)에 맡기고, 계산 패키지가 입력을 검증하고 결과를 가공한다. 레벨 50, 능력치 포인트 0~32·한 마리 합계 66 이하, 랭크 -6~6이다. 포인트는 환산 없이 엔진의 `evs`에 전달하며 특성은 명시한다.
- **지진 검증 계약.** 한카리아스와 메가 메타그로스의 싱글 대결에서 성격·공격자 포인트·랭크·도구·날씨·지형·방어 측 벽을 바꿔 비교했다. 생명의구슬·달인의띠·부드러운모래의 보정을 확인했고, 방어자는 메타그로스나이트를 유지했다. 지원 목록 밖의 도구와 소모 후 반복 효과는 이 계약에서 제외했다.
- 기준 결과는 제공된 16개 난수와 일치했고 범위는 102~120(58.3~68.6%), 확정 2타였다. 성격을 명랑에서 고집으로 바꾸면 110~132였고 그래스필드에서는 50~62였다. 당시 회귀 테스트 36개와 브라우저의 조건 변경·오류 시 결과 제거·초기화를 확인했다. 실기 대전 전수 검증은 하지 않았다.
- **결과 해석.** 지진 검증 화면은 중복을 포함한 난수를 보존하고 HP 대비 비율은 소수 첫째 자리, KO 확률은 둘째 자리 반올림으로 표시했다. 회복·턴 종료 피해·공격자 반동 기절은 제외했다. 엔진의 5~9타 확률 미산출(`null`), 9타 초과, 무효를 구별했다. 이 화면과 당시 실행기는 제거됐다. 현재 CLI 범위는 아래 절에 있다.

### 조건부 기술의 제품 규칙

아래는 싱글 계산기의 제품 설계다. 현재 CLI가 제공하는 1회 결과에 이어, 같은 기술을 반복할 때 상태를 다음 사용에 넘기는 처리와 웹 입력 화면을 구현할 예정이다. 반복 KO의 대표 타수와 확률 표시 정밀도는 미정이다. 기술별 분류와 추가 입력은 [조건 정의](../packages/calculator/data/champions/conditions.json), 현재 선택 범위는 [카탈로그](../packages/calculator/data/champions/README.md#계산기-선택-목록)를 따른다.

- **입력의 적용 범위.** 포켓몬의 상태이상은 하나만 선택해 공격·방어·스피드에 공유한다. 상대별 날씨·지형·중력과 진영별 벽은 해당 대결의 비교에서 공유한다. 기술을 바꾸면 이전 기술에만 해당하는 입력을 계산에서 뺀다. 기술이 여러 규칙에 해당하면 함께 적용한다. 코골기를 확정하면 기존 상태를 수면으로 교체하고 이전 상태는 복원하지 않는다. 포이즌힐은 턴 종료 회복이므로 계산용 특성에서 제외한다.
- **횟수·강화 조건.** 연속기는 실제 적중 수만 입력하고 기본은 기술별 최대치다. 트리플악셀은 1~3타(20→40→60), 찍찍베기는 1~10타, 고정 2타 기술이나 스킬링크는 입력이 필요 없다. 쓰러진 아군 0~5, 피격 0~6, 비축 0~3은 기본 0이다. 토해내기는 0회면 사용 불가다. 보복은 상대별 토글이고 스피드로 추정하지 않는다. 강화 위력 토글은 기본 OFF이며 사용자 이력(직전 실패·랭크 하락 등)과 상대별 이력(승부굳히기·눈사태)을 구분한다.
- **반사·성공·1회 제한.** 카운터·미러코트는 맞는 분류의 상대 기술 데미지를 2배, 메탈버스트·앙갚음은 1.5배로 반사한다. 상대 기술이 비면 그 행에 입력을 안내하고 방어 비교 선택은 요구하지 않는다. 반사, 첫 턴 전용, 자기 기절, 연속 사용 제한, 비축·도구 소모, 사용 후 타입 상실 기술은 해당 규칙에 따라 한 번의 사용 결과와 1타 KO만 표시한다. 기습·기선제압·힘껏펀치·트림·비장의무기는 성공 조건을 충족한 것으로 본다. 아이언롤러는 1회만 표시하며 필드가 없으면 0과 사용 불가 사유를 반환한다.
- **반복 KO의 경계.** 시작 HP 1~100%(기본 100%)에서 같은 기술이 명중한 횟수를 센다. 각 난수에서 남은 HP·도구·랭크·필드 변화를 다음 타격에 전달하고, 다른 상대와 화면 입력은 유지한다. 준비·재충전·지연 턴, 명중·급소 발생 확률, 회복·턴 종료 피해·반동 기절·자동 상태 부여/치료·교체·도구 이동은 제외한다. 셸암즈는 첫 타격 직전 정수 판정값이 같으면 물리 접촉·특수 비접촉 경로를 각 50%로 나누고, 같은 비교의 후속 사용에서도 최초 분류를 유지한다.
- **벽·지형·도구의 적용 시점.** 깨트리기·사이코팽·레이징불은 타격 전에 상대 벽을 제거한다. 아이스스피너는 성공한 타격 후 지형을 지운다. 탁쳐서떨구기와 애크러뱃은 사용자가 위력 강화 여부를 ON/OFF로 지정한다. 반감열매는 첫 발동 타격에만 쓰이고, 노말주얼은 첫 발동 기술 사용 전체를 1.3배로 강화한다. 하양허브는 랭크 변화 ON에서 음수 랭크를 한 번 0으로 되돌린다. 풍선은 맞은 뒤 터지며 풍선으로 땅 기술을 무효화하면 유지한다.
- **HP와 생존.** 하드프레스는 난수별 남은 HP로 다음 타격의 위력을 갱신한다. 멀티스케일은 매 타격 직전 최대 HP 여부를 본다. 1 HP 생존 처리는 범위에서 제외하며 기합의띠·기합의머리띠·옹골참은 선택 목록에서 뺀다. 탈은 온전함 기본 ON이며 첫 유효 타격 흡수와 최대 HP의 1/8 손실 뒤 남은 타격을 계산한다. 일반 도구의 선택 범위는 [카탈로그의 선택 목록](../packages/calculator/data/champions/README.md#계산기-선택-목록)을 따른다.
- **랭크 변화.** 확정 효과만 반영하는 토글은 기본 ON이며 OFF일 때는 입력한 시작 랭크를 유지한다. 일렉트로빔·메테오빔은 첫 타격 전 특공 +1, 스케일샷은 마지막 타격 후 방어 -1·스피드 +1이다. 클리어스모그는 첫 성공 직후 상대 랭크를 0으로 만들고, 마지막일침의 KO 후 상승은 해당 상대의 계산에서 끝난다.
- 공격자에게 적용되는 적중 후 변화는 특공 +1(플레어송), 특공 -2(용성군, 리프스톰, 오버히트, 골드러시), 방어 +1(배리어러시), 방어 -1(스케일노이즈), 방어·특방 -1씩(아머캐논, 인파이트, 들이받기), 공격·방어 -1씩(엄청난힘), 스피드 +1(아쿠아스텝, 오라휠, 니트로차지, 고속스핀, 개척하기), 스피드 -1(암해머, 아이스해머)다.
- 방어자에게 적용되는 적중 후 변화는 공격 -1(천추지한, 와이드브레이커, 찬물끼얹기, 덤벼들기, 트로피컬킥), 방어 -1(불꽃채찍, G의힘), 특공 -1(매지컬플레임, 엄습하는일격, 바크아웃, 소울크래시, 벌레의저항), 특방 -1(사과산), 특방 -2(애시드봄, 루미나콜리전), 스피드 -1(땅고르기, 드럼어택, 일렉트릭네트, 얼어붙은바람, 로킥, 머드샷, 달려들기, 암석봉인)다.

### 싱글 CLI의 필드와 접지 판정

- 포켓몬·폼, 성격, 특성, 도구, 기술은 엔진 호출 전에 카탈로그 ID나 영문 이름을 정식 엔진 이름으로 변환한다. 빈 특성은 `No Ability`를 명시한다. 이름을 해석할 수 없으면 입력 오류를 반환한다. 습득 가능 기술과 특성 조합의 적법성은 후속 범위다.

- 아이언롤러는 필드가 없으면 데미지 0으로 처리한다. 필드 없이도 1회 데미지를 표시하려던 예외를 제거하고 게임의 사용 조건을 따른다. 필드가 있으면 1회만 계산한다.
- 중력이 켜져 있으면 공중날기·뛰어오르기·플라잉프레스·무릎차기는 사용할 수 없다. CLI는 이 네 기술과 필드 없는 아이언롤러에 데미지 0과 `unavailableReason`을 반환해 사용 불가 사유를 표시한다.
- `@smogon/calc@0.12.0`은 검은철구로 접지한 상대에게도 부유·천정부지의 땅 기술 무효를 적용한다. 계산 패키지는 엔진이 그 특성을 무효 사유로 반환한 땅 공격만 다시 계산한다. 검은철구와 실제 필드 조건을 적용하고 반환한 상대 정보에는 원래 특성을 보존한다.
- 풀 HP 질풍날개의 비행 공격과 그래스필드에서 접지한 사용자의 그래스슬라이더는 우선도 +1을 기술 생성 시 전달한다. 설치 엔진은 질풍날개를 차단 검사 후에 처리하고 그래스슬라이더의 우선도 상승을 생략한다. 최종 차단 여부는 엔진의 사이코필드·테일아머·여왕의위엄 판정을 따른다.
- 공통 계산 함수가 JSON의 필수 객체와 각 입력의 형식·허용값을 검사한다. CLI는 입력 오류가 난 항목의 경로를 표준 오류로 출력하고 종료 코드 1을 반환한다.
- CLI로 필드 169건, 기본 데미지 33건, 날씨 80건을 재검증했다. 아이언롤러는 필드 없는 두 상대에게 0이었고, 워시로토무의 부유·검은철구 조합은 지진 134~158이었다.

### 조건부 기술을 공통 입력으로 호출한 결과

기술별 예외를 보정하기 전, 한카리아스·메가메타그로스·메가리자몽Y를 공격자로, 누리레느·하마돈·아머까오를 방어자로 사용했다. 기술별 추가 입력을 생략한 176종과 재현·대조 79건은 모두 CLI가 정상 종료했고 엔진 직접 호출과 결과가 일치했다. 이 중 66종의 144건은 조건별 기대 위력·데미지도 대조했다. 최초 176종 중 47종은 지정한 공격자가 배울 수 있는 기술이었다. 나머지 129종은 습득 제한을 적용하지 않고 엔진 기본 동작을 확인한 사례다. 47종 역시 여기서 확인한 것은 습득 조건까지다. 당시의 CLI 정상 종료와 엔진 결과 일치만으로 제품에서 성립하는 조합을 판정할 수 없다.

| 조건                           | 관찰한 기본 동작                                              | 제품 처리                                                         |
| ------------------------------ | ------------------------------------------------------------- | ----------------------------------------------------------------- |
| 2~5타 연속기 8종               | 타수 생략 시 모두 3타                                         | 기술별 타수 입력을 연결할 때 기본 5타 적용                        |
| 반사 기술 4종                  | 상대 기술을 전달하지 않으면 모두 데미지 0. 상대를 바꿔도 재현 | 상대 기술 입력을 안내하고 받은 데미지를 연결하는 작업은 후속 범위 |
| 토해내기·내던지기·폴터가이스트 | 각각 비축·던질 도구·상대 도구가 없으면 데미지 0               | 내던지기는 이번 CLI에서 사용 불가 사유까지 제공                   |
| 보복                           | 별도 입력 없이 사용자가 느릴 때 위력 50에서 100으로 변경      | 현재 CLI는 상대별 발동 입력을 사용하며 기본 OFF                   |

### 싱글 CLI의 능력치 포인트와 최종 스피드 입력 범위

공통 입력 함수에서 공격자와 방어자의 능력치 포인트를 별도로 검증한다. 한 능력치는 0~32의 정수, 한 마리의 합계는 최대 66이고 생략한 능력치는 0이다. 범위를 벗어나면 엔진 호출 전에 해당 입력 경로를 반환한다. 이 제한으로 비정상적으로 큰 포인트가 엔진의 16비트 랭크 연산에 들어가는 경우도 차단한다.

스피드 비교는 양쪽 최종 실수치를 그대로 표시하고 트릭룸에서 순서만 뒤집는다. 엔진 0.12.0의 챔피언스 모드는 999를 넘는 실수치를 999로 자르므로, 비교에는 같은 보정과 더 높은 상한을 쓰는 엔진의 9세대 스피드 함수를 사용한다. 일반 기술의 데미지는 999 초과도 허용한다. 양쪽 스피드 비율로 위력을 정하는 일렉트릭볼·자이로볼은 한쪽이라도 999를 넘으면 입력 오류를 반환한다. 보복은 상대별 `moveConditionSatisfied`, 애널라이즈는 공격자의 `abilityActive`로 발동을 선택하며 둘 다 기본 OFF다. 두 보정은 서로 독립적으로 적용하고 스피드 선후공을 추정하지 않는다. 코골기를 확정할 때 기술명을 검증하고 공격자의 상태를 수면으로 교체한다. 스피드 비교는 확정된 상태를 읽는다. 일반 마비는 스피드 절반이며, 속보는 상태이상이 있으면 1.5배가 되고 마비 반감을 생략한다.

곡예는 `abilityActive` 생략 시 ON이며 도구와 함께 지정하면 해당 도구 입력 오류를 반환한다. OFF는 도구 보유 여부와 관계없이 곡예 배율을 적용하지 않는다.

### 싱글 CLI의 내던지기 위력

챔피언스 엔진 0.12.0은 내던지기 위력을 도구표에서 다시 읽어 호출자가 전달한 위력을 덮어쓴다. 버전에 고정한 pnpm 패치로 내던지기 분기에서 전달한 위력을 우선한다. 고정한 Showdown 챔피언스 원본과 엔진의 위력이 다른 도구만 보정하고, 보유자가 던질 수 없는 메가스톤은 폼별로 판정한다. 공격자의 실제 도구를 유지해 생명의구슬 같은 첫 공격 보정도 엔진에 반영한다. 도구 미보유·투척 불가·서투름은 CLI에서 사용 불가 사유를 반환한다. 필드와 공격자의 시드가 일치하면 이미 소모된 도구로 처리해 위력과 데미지를 0으로 반환한다. 필드가 없거나 다른 필드에서는 시드 위력 10을 적용한다.

잠금 파일로 새로 설치한 환경에서 도구 166개와 무도구·서투름을 포함한 CLI 170건을 대조했다. 사용 가능 163건의 위력·16개 난수가 기대값과 일치했고, 사용 불가 7건은 데미지 0과 사유를 반환했다. 메가스톤 81개와 폼 382개의 30,942가지 조합 중 고정 Showdown 원본이 막는 177가지에서만 투척이 차단됐다.

### 싱글 CLI의 부자유친·셸암즈·탈

부자유친은 고정 원본의 공격기에서 `noparentalbond`·`charge`·`futuremove`가 있는 기술 17종을 추출해 추가 타격에서 제외한다. 엔진의 고정 데미지·일반 데미지 양쪽 경로에 적용한다. 원래 연속기의 타수는 유지한다. 온전한 탈을 상대로 구멍파기·솔라빔은 탈만 깨지며, 아이언테일은 둘째 타격이 명중한다. 당시 엔진 조사에서는 제외 기술 17종 × 방어 상태 3가지의 51건에서 부자유친 유무에 따른 타수·데미지·탈 손실이 일치했다. 51건에는 제품에서 함께 선택할 수 없는 입력이 포함됐다. 시드 4종은 필드 5가지(없음 포함)·탈 상태 2가지의 40건으로 투척 가능 여부와 위력을 검증했다.

부자유친은 부모 타격에 반감열매가 발동하면 도구를 비운 상대를 자식 타격에 넘긴다. 따라큐의 탈이 부모 타격을 막으면 열매가 남아 자식 타격에서 발동한다.

셸암즈는 첫 타격 직전에 레벨·위력과 랭크 적용 후의 공격/방어 및 특공/특방으로 구한 정수 판정값을 비교한다. 필드 시드처럼 공격 전에 바뀐 랭크를 반영한다. 첫 타격에서 선택한 분류는 그 계산이 끝날 때까지 고정한다. 후속 타격에서 능력치가 변하면 바뀐 능력치로 데미지만 다시 구한다. 화상·벽·도구 등은 분류를 정한 뒤 데미지에 적용한다. 동점이면 물리 접촉과 특수 비접촉을 각각 계산한다. CLI의 `categoryBranches`는 각 분류의 확률(0.5), 데미지 범위와 난수를 담는다. 전체 범위와 난수는 두 분기를 같은 비중으로 합친 1회 사용 결과다. 한 분류가 우세하면 `category`와 그 분류의 결과만 제공한다.

탈 특성을 선택한 따라큐는 `disguiseIntact` 생략 시 온전한 상태로 시작한다. 탈이 막는 첫 유효 타격의 기술 데미지는 0이며, 별도 필드 `disguiseHpLoss`에 최대 HP의 1/8(버림, 남은 HP 이내)을 기록한다. 남은 HP가 있으면 같은 사용의 다음 타격부터 원래 타격 순서와 위력으로 계산한다. 이미 깨진 폼·토글 OFF·틀깨기·타입 무효에서는 탈 파괴 손실이 발생하지 않는다. 멀티스케일과 성스러운칼·DD래리어트의 방어 랭크 무시에는 엔진의 기존 처리를 사용한다.

## D16. PokéAPI 공식 일러스트와 비상업적 운영·권리 고지

- **문제와 범위:** 계산 화면에서 포켓몬을 식별할 수 있는 이미지의 제공처와 스타일을 조사하고, 서비스의 운영 목적·권리 고지 방향을 정한다. 이미지 연결과 고지 UI는 아직 구현 범위에 포함하지 않는다.
- **선택과 대안:** PokéAPI Sprites의 `other/official-artwork` 정적 PNG로 이미지 스타일을 통일한다. HOME 이미지, 도트 이미지와 애니메이션도 제공되지만 공식 일러스트를 사용하는 방향으로 정했다. 이미지 없는 화면은 외부 이미지 의존성을 없애는 대안이다.
- **선택 이유:** 포켓몬을 식별할 수 있는 정적 일러스트로 화면의 이미지 스타일을 통일한다. 현재 계산 화면에는 애니메이션 재생이 필요하지 않다.
- **조사 결과와 후속 확인:** PokéAPI 데이터에서 한카리아스 ID `445`, 메가 메타그로스 ID `10076`을 확인했다. 메가진화를 기본 종의 도감 번호에만 연결하지 않아야 한다. 전체 포켓몬·폼 매핑과 이미지 전달 방식은 구현 단계에서 정하고 검증한다.
- **운영과 고지 방향:** 학습 및 정보 제공을 위한 비상업적 팬 프로젝트로 운영한다. 비상업적 목적, 포켓몬 이미지·명칭의 권리자, 관련 회사의 공식 승인·후원·제휴 관계 부재, PokéAPI 출처와 이미지 라이선스 링크를 표시할 예정이다. 고지의 위치와 컴포넌트 구성은 구현 단계에서 정한다.
- **권리 확인의 한계:** PokéAPI 저장소는 CC0를 표시하면서 이미지 저작권이 The Pokémon Company에 있다고 명시하고, 제3자의 권리 해결이나 필요한 허락의 확보를 보장하지 않는다. 이미지에 대한 개별 사용 허락은 확인되지 않았다. 다른 사이트의 사용 사례, 비상업적 목적과 권리자 고지를 권리자의 묵시적 허락 또는 적법성 확인으로 취급하지 않는다. 이 상태에서 이미지를 사용하는 제약을 유지하며 운영 범위 변경 시 사용 조건을 다시 검토한다.
- **현재 상태:** 이미지 제공처·형식과 대표 포켓몬·폼의 식별자를 조사하고 사용 방향을 정했다. 저장소의 이미지 연결·고지 UI·외부 이미지 설정은 미적용 상태다. 전체 지원 포켓몬의 이미지 존재 여부나 법적 사용 권한을 검증한 것은 아니다.
- **확인 자료:** [PokéAPI 이미지와 형식](https://github.com/PokeAPI/sprites#sprites), [PokéAPI 포켓몬·폼 ID 데이터](https://github.com/PokeAPI/pokeapi/blob/master/data/v2/csv/pokemon.csv), [이미지 저장소 라이선스](https://github.com/PokeAPI/sprites/blob/master/LICENCE.txt), [Pokémon 공식 이미지 사용 안내](https://support.pokemon.com/hc/en-us/articles/360000634094-Can-I-use-Pok%C3%A9mon-images-or-materials), [CC0와 제3자 권리](https://wiki.creativecommons.org/wiki/CC0_FAQ).

## D17. 로컬 PostgreSQL과 서비스·마이그레이션 역할 분리

- **문제와 범위:** 앱 연결 전에 로컬 DB의 실행·인증·권한을 독립적으로 확인하고, 실행 중인 앱의 자격증명으로 테이블 구조나 마이그레이션 이력을 변경하지 못하게 한다. [#8](https://github.com/nickwildee/champsparty/issues/8)의 로컬 구성 범위이며 배포용 DB 서비스는 선택하지 않았다.
- **실행 방식과 대안:** Homebrew PostgreSQL `18.7`을 설치하고 `brew services run postgresql@18`로 필요할 때 실행한다. Docker는 별도 런타임·컨테이너 관리가 추가되므로 현재 도입하지 않고, 환경 재현 등 필요가 생기면 검토한다. 로그인 시 자동 실행 대신 수동 시작·중지를 사용한다.
- **역할 분리와 대안:** `champsparty` DB의 소유자는 `champsparty_migrator`이고, 앱은 `champsparty_app`으로 접속한다. 단일 역할은 접속 정보 관리가 단순하지만 앱도 구조 변경 권한을 갖게 된다. 두 역할로 분리해 앱의 허용 범위를 데이터 처리로 제한하는 대신 비밀번호 두 개와 실행 목적별 환경 파일을 관리한다. 두 역할 모두 슈퍼유저·DB 생성·역할 생성·복제·RLS 우회 권한을 부여하지 않는다.
- **스키마·자동 권한:** migrator가 `public`과 `drizzle`을 소유한다. `public`은 서비스 테이블, `drizzle`은 마이그레이션 이력에 사용한다. DB와 두 스키마의 기본 `PUBLIC` 권한을 회수하고 앱에는 DB의 `CONNECT`와 `public`의 `USAGE`만 부여한다. `ALTER DEFAULT PRIVILEGES FOR ROLE champsparty_migrator IN SCHEMA public`로 새 테이블의 `SELECT`·`INSERT`·`UPDATE`·`DELETE`를 앱에 자동 부여한다. 이 규칙은 migrator가 생성하는 테이블에 적용되므로 마이그레이션 실행 역할을 유지해야 한다. 앱의 `CREATE`·`TEMP`·`TRUNCATE`·구조 변경·객체 삭제·이력 스키마 접근과 migrator 역할 전환은 허용하지 않는다.
- **비밀값 보관:** 역할마다 별도로 생성한 64자 무작위 16진수 비밀번호를 사용한다. `apps/web/.env.local`의 `DATABASE_URL`은 앱 역할, `apps/web/.env.migrations.local`의 `MIGRATION_DATABASE_URL`은 migrator 역할이다. 두 파일은 Git 제외와 권한 `0600`을 확인했다. 마이그레이션 전용 파일은 Next.js의 자동 로딩 대상에서 분리하고 D20의 마이그레이션 명령에서 명시적으로 읽는다. URL·비밀번호·해시를 문서나 이슈에 남기지 않는다.
- **로컬 인증과 관리 접속:** 두 프로젝트 역할의 IPv4 `127.0.0.1/32`·IPv6 `::1/128`·Unix 소켓에 `scram-sha-256` 규칙을 먼저 적용했다. DB 이름과 무관하게 적용해 다른 DB로 접속하며 후순위 `trust` 규칙을 선택하지 못하게 한다. 기존 `heoknoh` 관리 역할은 Homebrew 초기화 시 만들어진 로컬 슈퍼유저이며 비밀번호가 설정되지 않았다. 기존 관리 접속의 `trust` 규칙은 보존했다. 따라서 관리 역할의 비밀번호 인증까지 적용한 구성이 아니며, 이 설정을 배포 환경의 인증 정책으로 사용하지 않는다. 변경 전 HBA 파일은 같은 디렉터리의 `pg_hba.conf.champsparty-before-scram`에 보관했다.
- **로컬 검증.** PostgreSQL `18.7`에서 두 역할의 인증·권한 등 40개 항목을 확인했다. 수동 재시작 후 재접속과 잘못된 비밀번호 거부도 확인했다. 당시 앱 역할과 migrator 역할의 DB 직접 접속까지 검증했다. 앱 연결은 [D18 앱 DB 연결](#d18-앱-db-연결과-검증-방식), 마이그레이션은 [D20 인증 테이블·세션](#d20-better-auth-기반-인증-테이블과-세션-설정)에서 따로 확인했다. [권한별 검증 기록](https://github.com/nickwildee/champsparty/blob/bed1406a7c41d442b9a1ddcd97a14957f3f55477/docs/DECISIONS.md#d17-로컬-postgresql과-서비스마이그레이션-역할-분리)
- **확인 자료:** [PostgreSQL 비밀번호 인증](https://www.postgresql.org/docs/18/auth-password.html), [HBA 규칙과 적용 순서](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html), [기본 권한 설정](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html), [권한의 종류](https://www.postgresql.org/docs/18/ddl-priv.html).

## D18. 앱 DB 연결과 검증 방식

- **앱 연결.** [#9](https://github.com/nickwildee/champsparty/issues/9)에서 Drizzle과 pg로 로컬 DB를 연결했다. 연결 모듈의 소비자는 웹 서버 하나이므로 `getDb()`와 `closeDb()`를 앱에 둔다. [서버 연결 코드](../apps/web/src/server/db.ts)
- **풀 재사용.** 요청마다 접속을 만드는 비용을 줄이기 위해 같은 서버 실행 환경에서 풀 하나를 재사용한다. 개발 중에는 `globalThis`에 보관해 모듈이 다시 실행돼도 기존 풀을 사용한다. DB 접속 정보·설정을 바꾸면 개발 서버를 재시작한다.
- **연결 수와 대기 시간.** 로컬 시작값은 최대 10개, 연결 획득·새 연결에 5초, 유휴 연결 정리에 10초다. 최대 연결 수와 유휴 시간은 pg 기본값으로 두고 연결 문제를 빨리 알 수 있게 획득 제한을 정했다. SQL 실행 시간은 이 설정의 대상에서 제외된다. 배포 시 서버 실행 환경마다 풀이 생기므로 전체 연결 수를 다시 검토한다.
- **서버 경계와 오류.** `server-only`로 클라이언트의 import를 빌드에서 막는다. `DATABASE_URL`은 DB 기능을 처음 사용할 때 검사해 계산 화면의 빌드를 독립적으로 유지한다. 쿼리 오류는 호출자에게 전달하고 유휴 연결 오류에는 비밀값 없는 정보를 기록한다. 공통 모듈이 서버를 종료하거나 SQL을 자동 재실행하면 다른 요청이나 이미 처리됐을 수 있는 쓰기에 영향을 주므로 재시도는 호출자가 판단한다.
- **터미널 접속 확인.** 확인용 공개 API 대신 `pnpm db:check`가 앱과 같은 모듈을 호출해 `SELECT 1`, DB 이름과 역할을 읽는다. 기대 대상은 `champsparty`·`champsparty_app`이다. 환경 파일을 직접 지정하는 대안도 있었지만 앱과 파일 선택·우선순위를 맞추려고 `@next/env`로 `apps/web`의 개발 환경을 읽는다. 성공·실패 종료 코드는 0·1이고 명령이 만든 풀은 종료 시 정리한다. [접속 확인 코드](../apps/web/scripts/db-check.ts)
- **실행 도구.** 명령 프로세스에서만 `react-server` 조건과 `tsx`를 사용한다. Node.js 내장 TypeScript 실행 대신 개발 의존성을 추가해 앱의 TypeScript 모듈을 실행하며 타입은 별도로 검사한다. macOS의 POSIX 셸에서 확인했고 Windows에서의 실행은 미검증이다.
- **설치 예외.** pnpm 12가 `tsx` 의존성인 esbuild의 설치 후 스크립트를 차단했다. 플랫폼 실행 파일을 준비하고 버전을 검사하는 용도를 확인해 `esbuild@0.28.2`에 한해 허용했고, 일반 고정 lockfile 설치가 통과했다. esbuild 버전을 바꿀 때 다시 검토한다. 후속 인증 도구의 예외는 [D20](#d20-better-auth-기반-인증-테이블과-세션-설정)에 기록했다.
- **로컬 검증.** Node.js `26.13.1`·pnpm `12.19.0`·PostgreSQL `18.7`에서 `pnpm db:check`가 기대한 DB와 앱 역할을 확인했다. 정상·실패·풀 수명주기를 포함한 7개 시나리오를 점검했다. Next.js의 임시 클라이언트 코드는 DB 모듈을 가져올 때 빌드에서 거부됐다. 로컬 서버에서 DB 요청이 실패한 뒤에도 일반 페이지는 200을 반환했다.
- **검증 경계.** 풀 재사용은 같은 Node 실행 환경의 모듈 재로딩으로 확인했다. 실제 Next.js 편집 이벤트 전체, 배포 환경의 연결 수와 장애별 복구는 추가 검증 대상이다. 임시 페이지와 서버는 검증 뒤 제거했다. [연결·오류·격리 시나리오와 결과](https://github.com/nickwildee/champsparty/blob/921fe3e77d2523c4f078f15fb3a8a424e83438ef/docs/DECISIONS.md#d18-앱-db-연결과-검증-방식)
- **확인 자료:** [pg Pool 설정·연결 획득·유휴 정리](https://node-postgres.com/apis/pool), [풀 크기와 서버별 연결 수](https://node-postgres.com/guides/pool-sizing), [Next.js 개발 서버의 HMR](https://nextjs.org/docs/app/api-reference/cli/next#next-dev-options), [Node.js 전역 객체](https://nodejs.org/api/globals.html#global), [Next.js 서버 전용 코드 검사](https://nextjs.org/docs/app/getting-started/server-and-client-components#preventing-environment-poisoning), [Next.js 외부의 환경 파일 로딩](https://nextjs.org/docs/app/guides/environment-variables#loading-environment-variables-with-nextenv), [Node.js TypeScript 실행](https://nodejs.org/api/typescript.html), [pnpm 설치 스크립트 허용 범위](https://pnpm.io/settings/build#allowbuilds).

## D19. 네이버 단일 로그인과 인증 데이터의 기본 구조

- **로그인 범위.** MVP의 로그인 제공자는 네이버 하나다. 별도의 이메일·비밀번호 가입, 메일 인증, 비밀번호 복구와 로그인 이후의 네이버 API 기능은 범위에서 제외했다.
- **사용자와 외부 계정.** Better Auth 기본 모델을 따라 앱 사용자는 `user.id`로, 네이버 계정은 `account.providerId`와 `account.accountId`로 구분한다. `account.userId`가 두 레코드를 연결한다. 네이버 식별자를 사용자 테이블에 직접 넣는 대안도 있었지만, 이 구조에서는 앱 데이터가 로그인 제공자의 식별 방식에 의존하지 않는다. `user`에는 기본 필드 7개(`id`, `name`, `email`, `emailVerified`, `image`, `createdAt`, `updatedAt`)를 사용한다. [인증 스키마](../apps/web/src/server/auth-schema.ts)
- **세션과 토큰.** 앱의 로그인 상태는 `session.userId`에 연결된 Better Auth 세션으로 확인한다. 네이버 API용 토큰 필드는 `account`에 있다. 제공자 토큰의 별도 보관·갱신 정책은 후속 검토 사항이다. 앱 세션의 만료·갱신 설정과 검증은 [D20](#d20-better-auth-기반-인증-테이블과-세션-설정), 네이버 연락처 이메일 제공 없이 계정을 연결하는 방식과 검증은 [D21](#d21-네이버-이용자-식별자와-내부용-이메일)에 기록했다.
- **저장 세팅의 소유자.** 향후 사용자가 명시적으로 저장한 내 포켓몬 세팅은 앱의 `user.id`에 연결하는 방향이다. 저장 테이블·API·접근 제어와 사용자 삭제 시 세팅 처리 방식은 세팅 저장 기능에서 정한다. 편집 중인 화면과 상대 목록은 D05에서 정한 브라우저 로컬 복원 대상이다.

## D20. Better Auth 기반 인증 테이블과 세션 설정

- [#10](https://github.com/nickwildee/champsparty/issues/10)에서 기존 PostgreSQL과 Drizzle 연결 위에 Better Auth의 기본 인증 서버를 구성했다. 런타임 `better-auth`와 스키마 생성 도구 `auth`를 `1.7.26`으로 맞추고, `drizzle-kit 0.31.11`을 사용한다. 기존 `drizzle-orm 0.45.4` 및 `pg 8.23.1`과의 peer 의존성 검사를 통과했다.
- 생성 도구 전용 `auth-schema.config.ts`에서 Better Auth의 기본 스키마를 만든다. 실제 인증 요청에는 `auth.ts`가 앱 DB에 연결하고 인증 비밀값을 사용한다. Better Auth가 생성하는 `user`, `account`, `session`, `verification`을 그대로 채택하고, Drizzle Kit가 만든 SQL과 메타데이터를 함께 보관해 같은 변경을 검토하고 다른 개발 환경에도 적용할 수 있게 했다.
- 수동 SQL 실행도 가능하지만, Drizzle Kit를 통해 저장소의 변경과 실제 DB의 적용 이력을 연결한다. D17의 역할 분리를 유지하기 위해 마이그레이션 명령은 앱 접속 정보와 별도의 `.env.migrations.local`을 사용한다. 로컬 `champsparty` DB와 `champsparty_migrator` 역할만 허용하고, 실행용 앱 역할에는 서비스 테이블의 행 작업 권한을 둔다.
- 이메일·비밀번호 로그인을 비활성화했다. 세션은 PostgreSQL에 저장하며, 생성 또는 갱신 후 7일 동안 유효하고 하루가 지난 뒤 로그인 상태를 확인하면 7일로 연장한다. 쿠키 캐시를 쓰면 DB 조회를 줄일 수 있지만 종료된 세션이 캐시 만료까지 유효하게 보일 수 있다. 초기에는 상태 확인에 DB 최신 값을 쓰고 실제 부하를 확인한 뒤 캐시 필요성을 다시 판단한다.
- 세션 생성 때 받을 수 있는 접속 IP와 `User-Agent`는 기본 필드에 저장한다. 오류 환경을 좁히고 접근을 조사할 때 참고한다. 실제 배포에서의 IP 기록과 비로그인 반복 요청 제한은 [#21](https://github.com/nickwildee/champsparty/issues/21)에서 검증한다.
- `getAuth()`는 인증 기능을 처음 호출할 때 환경변수를 검사하고 인스턴스를 생성한 뒤 같은 서버 모듈에서 재사용한다. Next.js의 `GET`·`POST`는 공식 `toNextJsHandler`를 통해 Better Auth에 전달한다. 요청이 들어오는 시점에 `getAuth()`를 호출하도록 함수를 넘겨, 파일을 읽을 때 인증 환경변수를 요구하지 않도록 했다.
- Drizzle Kit가 직접 사용하는 `esbuild@0.25.12`와 `@esbuild-kit/esm-loader`를 거쳐 들어오는 `esbuild@0.18.20`의 설치 후 스크립트를 추가 허용했다. 기존 `0.28.2` 허용을 유지하고 배포 직후의 설치 제한을 우회하는 예외는 추가하지 않았다. macOS의 일반 frozen-lockfile 설치를 확인했다. Windows에서의 실제 설치·실행은 미검증이다.
- 로컬 PostgreSQL에서 마이그레이션 재실행 후 같은 SQL의 적용 이력이 1건임을 확인했다. 인증 테이블의 기본 키·외래 키·고유 제약과 앱 역할의 행 권한을 확인했고, 앱 역할에는 테이블 생성 및 이력 스키마 접근 권한이 없음을 확인했다. 앱의 Better Auth 어댑터로 네 테이블을 조회했다.
- 실제 Next.js 개발 서버에서 쿠키 없는 세션 조회는 `200`과 `null`, 로그아웃 요청은 `200`과 성공 응답을 반환했다. 세션의 최초 만료일·하루 전후의 갱신·만료 세션 거부와 IP·`User-Agent` 기록은 별도의 메모리 저장소로 검증했다. 인증 URL·비밀값·DB URL을 비운 프로덕션 빌드도 통과했다. 네이버 앱·제공자 연결은 #11, 실제 계정과 쿠키·DB를 포함한 통합 검증은 #13 범위다.
- [Better Auth 기본 스키마](https://better-auth.com/docs/concepts/database#core-schema), [세션 관리](https://better-auth.com/docs/concepts/session-management), [Next.js 연동](https://better-auth.com/docs/integrations/next#create-api-route), [Drizzle Kit 마이그레이션](https://orm.drizzle.team/docs/drizzle-kit-migrate)

## D21. 네이버 이용자 식별자와 내부용 이메일

- [#11](https://github.com/nickwildee/champsparty/issues/11)에서 Better Auth 기본 네이버 제공자를 연결했다. 계정 연결에는 네이버가 이 앱에 발급한 `response.id`를 사용한다. 개인 연락처가 필요한 기능이 없어 네이버의 이메일·프로필 기본 요청을 끄고 표시 이름은 `트레이너`로 고정한다.
- Better Auth와 현재 사용자 테이블은 고유한 이메일 값을 요구한다. 연락처 이메일 동의를 추가하는 대안 대신, 식별자의 원문을 SHA-256으로 해시한 소문자 16진수 문자열에 `@naver.invalid`를 붙인다. 같은 식별자의 값은 일정하고 원문의 대소문자 차이도 해시에 반영된다. 이메일 인증 상태는 `false`로 유지하며 연락·메일 발송·계정 복구에는 사용할 수 없다.
- 네이버 키 두 개가 모두 설정됐을 때만 제공자를 등록한다. 로컬 허용 출처는 Better Auth가 `BETTER_AUTH_URL`에서 읽는 기본 동작을 사용한다. 두 키가 모두 없거나 한쪽만 설정된 세 경우에 비로그인 세션 조회와 로그아웃은 HTTP 200을 반환하고 네이버 로그인 시작은 거부됐다.
- 네이버 개발자센터에서 발급한 앱의 `Client ID`와 `Client Secret`을 설정한 뒤, 로컬 Next.js 서버에서 네이버 인증 URL을 생성했다. 콜백 주소가 등록값과 일치했으며, Git에 포함될 파일·브라우저 정적 파일·로그인 시작 응답·잘못된 요청의 오류 응답에서 Client Secret이 발견되지 않았다.
- 네이버 토큰·프로필 응답을 대체하고 메모리 저장소를 사용해 Better Auth 콜백을 실행했다. 식별자만으로 가입하고 동일 식별자로 다시 로그인했을 때 같은 사용자의 세션이 생성됐다. 대소문자만 다른 식별자는 서로 다른 계정이 됐고, 식별자가 누락되면 계정이 생성되지 않았다. 응답에 별명·연락처 이메일·사진이 들어온 경우에도 사용자 레코드에는 표시 이름 `트레이너`와 내부용 이메일이 저장됐고 사진은 비어 있었다. 실제 네이버 동의와 콜백을 거치는 통합 검증은 #13에 남아 있다.
- [네이버 이용자 식별자와 프로필](https://developers.naver.com/docs/login/devguide/devguide.md#332-로그인한-회원의-네이버-로그인-사용-여부), [Better Auth의 이메일 없는 제공자 처리](https://better-auth.com/docs/concepts/oauth#handling-providers-without-email)

## D22. GitHub Actions 기본 검사

- [#14](https://github.com/nickwildee/champsparty/issues/14)에서는 GitHub 호스팅 Ubuntu의 `verify` 작업 하나에서 기존 루트 명령을 순서대로 실행한다. 여러 작업으로 나누면 동시에 검사할 수 있지만 각 작업에서 실행 환경을 준비해야 한다. 한 번 설치하고 처음 실패한 단계를 PR에 표시하는 구성을 선택했다.
- Node.js는 `.node-version`, pnpm은 루트 `package.json`의 `packageManager`를 따른다. 루트 lockfile을 기준으로 pnpm 저장소 캐시를 재사용하고 매번 고정 lockfile 설치를 실행한다. 두 외부 액션은 커밋 SHA로 고정했다. 워크플로 토큰 권한은 `contents: read`이며 checkout 후 Git 자격 증명을 보관하지 않는다.
- 같은 PR 또는 `main`에서 새 실행이 시작되면 진행 중인 이전 실행을 취소한다. PR 대상을 나중에 `main`으로 바꾸는 경우도 검사하도록 `edited`를 포함했다. 이 선택으로 제목이나 본문만 편집해도 검사가 다시 실행된다.
- [성공 실행](https://github.com/nickwildee/champsparty/actions/runs/44733946241)에서 Node.js `26.13.1`·pnpm `12.19.0`, 캐시 복원, 고정 설치, 서식, 두 패키지의 린트·타입 검사와 웹 프로덕션 빌드를 확인했다. 앱 인증 비밀값과 DB 연결은 사용하지 않았다.
- [실패 실행](https://github.com/nickwildee/champsparty/actions/runs/44733820876)에서는 임시 `package.json` 서식 오류로 해당 단계가 종료 코드 1을 반환했고 린트·타입·빌드는 건너뛰었다. 검증용 변경은 원복했다. 같은 PR에 새 커밋을 푸시한 뒤 [이전 실행의 취소](https://github.com/nickwildee/champsparty/actions/runs/44733772159)도 확인했다.
- PR 검증 당시 `main`에는 필수 상태 검사가 없었다. 2026-11-25에 `main`에 적용된 규칙을 조회해 `verify`가 필수 상태 검사임을 확인했다. `main`의 `55b3ac1` 푸시에서도 검사가 통과했고 이슈 #14는 종료됐다. ## 앞으로 결정 기록을 갱신할 때

- 결정을 바꾸면 기존 결정 번호와 배경을 보존하고 무엇이 왜 바뀌었는지 적는다. 대안의 장단점, 선택의 제약, 다시 판단할 조건을 구체적으로 남긴다.
- 판단을 바꾼 관측값에는 버전·조건·결과·한계를 붙이고 실행 원본인 테스트, PR 또는 보존 커밋을 연결한다. 학습 대화나 승인 경위는 기록 범위에서 제외한다.
