## 기록을 읽는 기준

- 이 문서는 대화에서 선택한 방향과 그 이유를 기록한다. 구현 완료 보고서가 아니다.
- **합의:** 현재 요구사항과 작업 방향으로 채택한 내용.
- **구현 방향:** 사용할 구성을 정했으나 버전·설정·실행 결과는 확인하지 않은 내용.
- **미정·검증 필요:** 구현 계약이나 실제 실행 결과로 확정할 내용.
- D01~D12의 최초 작성 기준일은 2026-11-16이다. 저장소 초기 설정과 문서 인계의 확인 결과는 D12, 개발 도구 검증 결과는 D13에 기록했다. 앱 기능의 실행 검증 결과와 성능 개선 수치는 아직 없다.
- 원문 대화 전체의 전사본이 아니라 주요 질문, 수정과 선택 이유를 정리한 기록이다. 이후 중요한 논의도 같은 기준으로 추가한다.

## D01. 숙련자의 세팅 조정을 위한 현재 결과 표시

- **배경:** 사용자는 이미 실전 포켓몬을 다룰 수 있다. 직접 정한 여러 상대에 대한 가능성을 한눈에 보고 싶어 한다.
- **합의:** 현재 입력의 스피드, 대미지 범위, KO 타수·확률, 결정력·내구를 제공한다.
- **사용자 수정:** 변경 전후를 비교할 필요가 있는지에 대해, 현재 능력치에서 어떤 결과가 나오는지만 보여 주는 것이 목적이라고 명확히 했다.
- **검토했던 대안:** 변경 전후 비교, 변화 알림, 파티 취약점 분석과 추천.
- **선택 이유:** 사용자가 판단할 수 있는 계산 정보를 제공하고 입력·확인 동선을 단순하게 유지한다.
- **범위:** 비교 이력, 자동 추천과 취약점 보고서를 현재 MVP에 포함하지 않는다.

## D02. 챔피언스만 지원하고 기존 계산 엔진 활용

- **배경:** 사용자는 직접 구현의 주된 부담을 많은 데이터의 재입력으로 보았다. 지원 게임을 챔피언스로 제한하면 직접 구현도 가능하지 않은지 검토했다.
- **합의:** `@smogon/calc`를 활용한다. 직접 계산 엔진 전체를 새로 만드는 방향은 채택하지 않는다.
- **사용자 선택:** 참고 서비스가 같은 계열의 엔진을 사용한다는 논의 이후, 기존 엔진을 가져다 쓰는 방향으로 변경했다.
- **대안:** 챔피언스 전용 엔진 직접 구현, 여러 게임을 지원하는 범용 계산기 구성.
- **선택 이유:** 기존 계산 로직과 데이터를 활용하고, 이 프로젝트의 핵심인 다수 상대 입력·즉시 갱신·저장 경험에 집중한다.
- **검증 필요:** 실제 설치할 배포 버전의 챔피언스 지원, 데이터 범위, 능력치 입력 변환과 난수 결과. 저장소 소스에서 지원 코드가 보인다는 사실만으로 설치 버전까지 검증한 것으로 쓰지 않는다.

## D03. 회복 효과는 제외하고 도구별 지원을 구분

- **초기 아이디어:** 자뭉열매와 먹다남은음식 같은 회복을 고려한 KO 타수 계산.
- **변경된 합의:** 회복 효과를 포함한 전투 진행 계산은 MVP에서 제외한다. 시작 HP는 100%이며 랭크는 포켓몬별 입력으로 제공한다.
- **사용자 이유:** 파티 준비를 위한 계산기에 전투 내부의 변수를 지나치게 넣으면 제공할 정보와 범위가 커진다고 판단했다.
- **이후 논의:** 엔진의 회복 및 반감열매 지원 여부와, 부족한 처리의 추가 구현 가능성을 확인했다.
- **현재 기준:** 가능성 조사가 회복 기능의 재도입 승인을 뜻하지 않는다. 반감열매의 첫 타 감소와 반복 공격 중 소비는 별도로 검증한다.
- **확률의 의미:** 동일 기술을 N회 사용해 모두 명중했을 때 N회 이내에 쓰러뜨릴 확률로 해석한다. 앞서 합의한 이 의미는 유지하며, 이후 철회된 회복 반영은 제외한다.
- **검증 필요:** 정확한 KO 확률이 성립하는 입력 범위와 엔진의 정밀도. 추가 보완이 필요하면 범위와 방법을 먼저 논의한다.

## D04. 공통 내 세팅과 영역별 상대 목록

- **합의:** 스피드·공격·방어의 세 영역에서 내 포켓몬 세팅을 공유하고, 상대 목록은 영역별로 독립시킨다.
- **사용자 요구:** 상대는 추가 버튼으로 한 마리씩 넣고 최대 5마리까지 사용할 수 있다. 5마리를 반드시 입력할 필요는 없다.
- **대안:** 처음부터 다섯 개의 빈 폼을 표시하거나 각 영역에 내 세팅도 따로 유지하는 방식.
- **선택 이유:** 하나의 내 세팅을 조정하면서 각 목적에 맞는 대비 대상을 확인한다. 필요한 입력만 추가한다.
- **화면 방향:** PC가 우선이며 모바일도 편리하게 지원한다. 미적인 장식보다 수정 동선과 결과 확인을 중시한다.

## D05. 기준 세팅 저장과 작업 화면 복원을 분리

- **배경:** 사용자는 내 포켓몬 세팅을 저장하고 나중에 불러와 조정하고 싶어 한다. 마지막 입력을 복원하는 편의도 함께 검토했다.
- **합의:** 내 포켓몬 세팅은 명시적으로 계정에 저장한다. 편집 중인 전체 작업 화면은 브라우저 로컬에서 자동 복원한다.
- **대안:** 모든 입력을 계정에 자동 저장하거나 전체 작업 화면을 명시적 저장 단위로 삼는 방식.
- **선택 이유:** 저장한 기준 세팅과 실험 중인 입력을 구분하면서 반복 입력 부담을 줄인다. 계정 저장본은 기기를 바꾸어 불러올 수 있다.
- **불러오기 규칙:** 사용자가 선택한 저장 세팅으로 내 입력을 교체하되 상대 목록은 유지한다. 이전 입력을 모두 별도 이력으로 보관하지 않는다.
- **범위:** 작업 초안의 기기 간 자동 동기화와 전체 파티·상대 목록의 계정 저장은 추가하지 않는다.

## D06. 편집 중인 입력을 서버 갱신으로 덮어쓰지 않음

- **논의의 핵심:** 저장한 한카리아스 세팅을 불러와 수정하는 중에 저장 목록이 다시 조회되더라도, 현재 편집값이 원래 저장값으로 돌아가면 안 된다.
- **합의:** 저장 데이터를 조회하는 상태와 계산기에 적용한 작업 입력을 분리한다. 명시적 불러오기에서만 저장 데이터를 작업 입력에 적용한다.
- **갱신 방향:** 목록을 열거나 저장·수정·삭제 결과를 반영하는 등 필요한 시점에 서버 데이터를 갱신한다. 노력치 입력 변경을 서버 재조회와 연결하지 않는다.
- **복원 규칙:** 이전 로컬 작업을 확인·복원한 뒤 자동 저장을 시작한다.
- **검증할 흐름:** 불러오기 후 수정 → 서버 목록 갱신 → 입력 유지, 새로 열기 → 기존 초안 복원 → 이후 변경 저장.
- **미정:** Query의 구체적인 캐시 시간과 재조회 옵션, 로컬 저장 형식과 갱신 방식.

## D07. 작은 풀스택 모노레포로 시작

- **합의:** Next.js + TypeScript를 사용하고, 웹과 서버 기능을 한 Next.js 애플리케이션에서 제공한다. 계산 로직은 별도 패키지로 분리한다.
- **현재 구성 방향:** `apps/web`, `packages/calculator`와 pnpm 워크스페이스. 아직 실제 폴더나 패키지 생성이 완료되었다는 뜻은 아니다.
- **대안:** 처음부터 독립 API 서버를 두거나 여러 공유 패키지와 추가 모노레포 도구를 함께 도입하는 방식.
- **선택 이유:** 현재 서버의 핵심 역할은 인증과 개인 세팅 저장이다. 지금 필요한 경계부터 두고 운영·개발 구성을 작게 유지한다.
- **사용자 기준:** 실제 필요가 생겼을 때 사용하고, 이후 필요한 경우 마이그레이션한다는 방향에 동의했다.
- **재검토 조건:** 서버의 독립 배포 등 구체적인 요구가 생겼을 때 분리를 검토한다. 나중에 쓸 수도 있다는 이유만으로 구조를 미리 늘리지 않는다.

## D08. 계산은 브라우저, 계산 패키지는 입력과 출력에 집중

- **구현 방향:** 현재 입력을 계산 엔진이 받을 형태로 변환하고, 결과를 화면에서 사용할 형태로 정리하는 계산 로직을 `packages/calculator`에 둔다. 계산은 브라우저에서 수행한다.
- **대안:** 입력을 바꿀 때마다 서버에 계산 요청을 보내는 방식.
- **선택 이유:** 실시간 조정에 필요한 계산을 네트워크 왕복과 분리하고, 계산 로직을 화면 코드와 별도로 검증한다.
- **경계:** 계산 패키지는 UI, 인증, DB 연결과 로컬 저장을 직접 관리하지 않는다.
- **감수할 점:** 브라우저로 전달되는 데이터·코드 크기와 모바일의 계산 응답성을 실제로 확인해야 한다.
- **검증과 개선:** 입력 반응, 계산 시간과 초기 로딩을 측정한 뒤 필요하면 최적화한다. Worker나 추가 캐시를 처음부터 필수로 정하지 않는다.

## D09. 작업 상태와 서버 상태를 목적에 맞게 관리

- **구현 방향:** 계산기 작업 입력은 React `useReducer`, 작은 UI 상태는 필요에 따라 `useState`, 저장된 서버 세팅은 TanStack Query로 관리한다.
- **계산 결과:** 현재 입력으로부터 파생한다. 입력과 별도로 수정 가능한 중복 결과 상태를 기본 구조로 두지 않는다.
- **대안:** 모든 입력을 개별 `useState`로 관리하거나 Zustand 같은 외부 상태 관리 도구를 사용하는 방식.
- **선택 이유:** 내 세팅 수정, 상대 추가·수정·삭제, 저장본 적용 등의 변경을 액션으로 모으고, 서버 데이터의 조회·갱신 상태는 별도로 다룬다.
- **주의할 해석:** `useReducer`를 선택했다고 렌더링 성능이 자동으로 개선되는 것은 아니다. 상태 공유나 구독 요구가 달라지면 다른 도구도 검토할 수 있다.
- **검증 필요:** 상태 변경 흐름, 계산 갱신, 복원 순서와 서버 갱신 중 입력 유지.

## D10. 계정 저장에 PostgreSQL·Drizzle, 로그인은 네이버

- **현재 구현 방향:** PostgreSQL과 Drizzle을 사용하고, 네이버 로그인을 Better Auth로 연동하는 방향으로 논의했다.
- **사용자 반응:** Drizzle의 역할을 설명받은 뒤 해당 방향에 동의했고, 로그인 제공자는 네이버를 선택했다.
- **대안:** 다른 ORM, 초기 후보였던 카카오 로그인, 인증 흐름을 직접 구성하는 방식.
- **선택 이유:** 사용자와 저장 세팅의 관계를 DB에 두고, TypeScript에서 스키마와 쿼리를 다루는 구성을 사용한다. 인증의 반복 작업은 라이브러리를 활용하는 방향이다.
- **범위:** 게임의 모든 계산 데이터를 DB에 다시 입력하는 것이 목적은 아니다. 계정에 저장할 사용자 세팅이 중심이다.
- **검증 필요:** 라이브러리 버전 호환성, 실제 네이버 로그인과 세션, DB 연결, 사용자별 저장 데이터 접근 제어.
- **미정:** DB 제공 서비스, 상세 스키마와 인증 설정. 네이버 로그인 선택을 특정 OAuth/OIDC 연동 방식의 실행 검증 완료로 쓰지 않는다. n3r 도입은 선택하지 않았다.

## D11. 생산성 중심 MVP 이후 실제 측정으로 개선

- **합의:** 핵심 기능이 정상적으로 동작하는 MVP를 먼저 만든 뒤 테스트와 성능 측정에서 발견한 문제를 개선한다.
- **사용자 의도:** 생산성을 위해 선택한 방법과 이후 정량적 개선을 이력서·면접에서 설명하고 싶어 한다. 일부러 품질을 떨어뜨려 개선 사례를 만들지는 않는다.
- **대안:** 처음부터 모든 예외와 최적화를 완성하거나, 수치 없이 개선을 주장하는 방식.
- **기록할 근거:** 당시 선택과 이유, 테스트 또는 측정 조건, 변경 전후 결과, 실제 사용자 흐름에서의 의미.
- **검증 방향:** 대표 계산 사례, 최대 상대 수에서의 입력·갱신, 저장·불러오기·복원, PC·모바일 주요 흐름을 확인한다.
- **미정:** 테스트 도구, 구체적인 성능 지표와 목표 수치. 같은 엔진을 쓰는 참고 서비스와 결과가 같다는 이유만으로 게임 규칙 전체의 독립 검증이 끝났다고 쓰지 않는다.

## D12. 초기 세팅보다 먼저 필요한 맥락 전달

- **상황:** 사용자는 새 저장소를 만들고 클론해 로컬 프로젝트에 연결했다. `.gitignore` 설정을 다른 대화에 요청한 상태다.
- **사용자 지적:** 로컬 프로젝트에는 아직 이 대화의 목적, 프로젝트 기획과 결정 내용을 전달하지 않았다.
- **변경된 순서:** 공통 `.gitignore` 작업은 마무리하되, Node.js·pnpm 설정과 구조 구성에 앞서 이 세 문서로 맥락을 전달한다.
- **선택 이유:** 기술명만 전달하는 것보다 목표, 범위와 결정 이유까지 전달해야 이후 작업을 같은 기준으로 진행할 수 있다.
- **인계 당시 상태:** 문서 작성 단계였으며 로컬 반영, 초기 설정 완료와 실행 검증 여부는 확인이 필요했다.
- **후속 확인(2026-11-16):** 초기 저장소 설정은 PR #1로 `main`에 병합되었고(`b988132`), 세 인계 문서는 올바른 위치에 배치되어 `docs/project-handoff` 브랜치에 커밋되었다(`f5a72e8`). 내부 문서 링크도 확인했다. 이 확인 시 인계 문서의 `main` 병합은 아직 확인되지 않았다.
- **초기 설정 검증:** `.gitignore`의 제외·허용 경로 11개와 `.gitattributes`의 LF 적용을 확인했다. 초기 검토 후 `.editorconfig`는 현재 효용이 낮아 생략하고, 별도 레포 운영 가이드는 중복 문서 관리를 줄이기 위해 제거했다. 공통 협업 원칙은 `AGENTS.md`에서 관리한다.
- **환경 조회 당시:** Node.js `23.7.0`, npm `10.9.2`, pnpm `10.18.1`, Corepack `0.31.0`을 확인했다. 당시에는 사용할 버전과 관리 방식이 미정이었다. 이후 합의와 적용 상태는 D13에 기록한다.
- **후속 작업:** 앱 초기화·의존성 설치·빌드와 계산·인증·DB 검증은 별도 작업이다.

## D13. 개발 도구 버전과 최소 워크스페이스 설정

- **문제:** 초기 셸은 Homebrew의 Node.js `23.7.0`과 기존 전역 pnpm `10.18.1`을 사용했다. 프로젝트에서 사용할 버전을 명시하고 다른 환경에서도 맞출 기준이 필요했다.
- **합의:** fnm으로 Node.js를 관리하고 Node.js `26.13.1`(26 LTS), pnpm `12.19.0`을 사용한다. 사용자에게 설치·셸 연결·루트 파일 3개·실행 검증·문서 갱신 범위를 설명한 뒤 진행 승인을 받았다.
- **대안과 이유:** 기존 Homebrew Node.js를 그대로 쓰거나 전역 버전만 교체할 수 있지만, 프로젝트별 전환과 버전 명시를 위해 fnm과 `.node-version`을 선택했다. 기존 pnpm 10 유지도 가능하나 새 프로젝트의 기준을 pnpm 12로 맞추기로 했다. 선택한 버전에서 애플리케이션 호환성 검증이 끝났다는 뜻은 아니다.
- **반영 범위:** `.node-version`에 정확한 Node.js 버전, 루트 `package.json`에 `private: true`·Node.js 허용 범위·정확한 `packageManager`, `pnpm-workspace.yaml`에 `apps/*`와 `packages/*`를 기록한다. `private: true`는 패키지의 npm 배포를 막고 GitHub 공개 설정에는 영향을 주지 않는다.
- **감수·보류:** 새 환경에서는 해당 도구 설치가 필요하다. Next.js 생성, 린터·포매터, 앱과 계산 패키지, 의존성 설치는 이번 범위에 넣지 않는다.
- **설치 경과:** 루트 파일 3개를 생성했다. 처음 `brew install fnm`은 샌드박스의 Homebrew 경로 쓰기 제한으로 실패했다. 이후 사용자가 fnm `1.39.0`, Node.js `26.13.1`, pnpm `12.19.0`을 설치했다. 앞서 안내한 셸 연결 명령이 기존 `.zshrc`의 마지막 줄바꿈 부재로 PATH 설정 뒤에 붙었고, 사용자가 이를 별도 줄로 수정했다. 현재 fnm 연결문은 `eval "$(fnm env --use-on-cd --shell zsh)"`다. pnpm 설치 중의 스크립트 허용 정책 경고는 실행 실패가 아니었다.
- **정적·제한된 환경 검증:** JSON·버전 값, YAML 구문·경로, LF, 내부 문서 링크와 `git diff --check`를 확인했다. 이전 대화에서는 샌드박스가 fnm 멀티셸 링크 생성을 막아 새 셸 자동 전환을 검증하지 못했다. 대신 설치된 Node.js의 bin 경로를 검증 프로세스의 PATH에만 지정해 Node.js `v26.13.1`, npm `11.20.0`, pnpm `12.19.0` 실행과 `pnpm -r list --depth -1`, `pnpm --filter champsparty list --depth -1`의 루트 인식을 확인했다. 영구 PATH 설정은 변경하지 않았다.
- **새 셸 검증(2026-11-17):** 샌드박스 안의 로그인·대화형 zsh에서는 fnm 멀티셸 링크 생성이 `Operation not permitted`로 막혀 실제 `node`가 Homebrew의 `v24.22.1`을 가리켰다. 권한 제한 밖에서 같은 방식으로 실행하자 `fnm current`와 `node --version`은 `v26.13.1`, npm은 `11.20.0`, pnpm은 `12.19.0`이었다. `node`와 `pnpm`은 fnm 멀티셸 경로에서 실행됐고 `pnpm -r list --depth -1`이 비공개 `champsparty` 루트를 인식했다. 새 셸 자동 전환과 최소 워크스페이스 실행의 완료 기준을 충족했다.
- **잠금 파일:** 사용자 터미널 작업 후 `pnpm-lock.yaml`이 생겼다. 현재 내용은 pnpm 자체 버전 관리 항목이며 앱 의존성 설치 완료를 뜻하지 않는다.
- **남은 검증:** 앱·계산 패키지 생성, 의존성 설치, 실행·빌드, 계산·인증·DB 연동은 별도 단계다. Next.js 생성 옵션, 린터·포매터와 스타일링 구성은 다음 단계에서 논의한다.
- **확인 자료:** [Node.js 26.13.1 LTS 배포](https://nodejs.org/en/blog/release/v26.13.1), [pnpm 12.19.0 배포](https://pnpm.io/blog/releases/12.19.0), [fnm 설치와 셸 설정](https://github.com/Schniz/fnm#installation).
